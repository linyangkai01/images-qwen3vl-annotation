## 1. 增量背景与动机

### 1.1 为什么这是一次"约束更正"而非新功能

基线 PRD 的硬约束写的是"用户因安全隐私原因不能提供原视频"，因此系统的默认形态是"用户在本机投喂视频、帧只发往用户自有模型服务"。这条约束的**技术含义被高估了**：

- 真实约束不是"不能解码视频"，而是**"解码后的帧只能送往三个指定去向"**。
- 这带来两个直接后果：
  1. 抽帧/解码是**允许且必要**的（否则无法把长视频压缩成可送模型的少量帧）；
  2. 模型接入不能只有一条 OpenAI 兼容路径，必须显式支持**三种可切换的解析途径**，并且每条途径的能力边界不同（YOLO 只出目标框，VLM 才出隐患事件）。

因此本次增量的定位是：**把"模型接入"从一个点（OpenAI 兼容 `/chat/completions`）扩展为一个可切换的路由层，并补齐与之配套的时长护栏、编码约定、凭据预留与结构化输出。**

### 1.2 三条途径的定位差异（这是本次增量的核心）

**途径一：本机 YOLO（`local_yolo`）**

- 定位：**离线、零网络、最快的通道 A 来源**。适合答辩演示与本地调试。
- 能力边界：**只能产出目标框（通道 A）**。它不具备多模态语义理解能力，无法产出隐患事件 JSON。
- 依赖：本机 Ultralytics 环境 + 本地权重文件。

**途径二：lab-server 上的 YOLO（`server_yolo`）**

- 定位：**算力更强、可复用实验室既有环境的通道 A 来源**。适合本机跑不动、或需要与实验室既有权重保持一致时使用。
- 能力边界：**同样只能产出目标框（通道 A）**。
- 依赖：`ssh` 免密可达 + `scp` 可搬运图片与标签 + 远程已激活的 YOLO 环境。执行方式是"本地上传图片 → 远程推理 → 下载标签"，本质是把本机算力换成远程算力。

**途径三：实验室私有多模态模型 API（`private_vlm`）**

- 定位：**唯一能同时产出通道 A（目标框）+ 通道 B（隐患事件）的途径**，也是毕设主通道。
- 能力边界：能出目标框，也能出隐患事件 JSON；但受算力限制，**单次只能处理 1 分钟以内的视频**。
- 接口契约（用户原话，必须严格遵守）：
  - URL：`http://119.23.145.227:38091/api/generate`
  - 方式：POST
  - 请求体：`{"model": "qwen3-vl:30b-a3b-thinking-q8_0", "prompt": "...", "options": {"temperature": 0.7, "max_tokens": 8192}, "stream": false, "images": ["base64编码1", "base64编码2"]}`
  - 图片：先转 **base64**，多图之间用**英文逗号**隔开
  - 认证：**Bearer Token**，token 由用户后续自行配置（**代码必须预留配置项**）

**辅助途径：mock（`mock`）**

- 定位：**离线替身**，不联网，用于无视频/无模型的干净环境跑通全链路（沿用基线 P0-7）。
- 能力边界：两条通道都能"假装"产出，用于链路验证与答辩兜底。

### 1.3 增量边界（与基线的关系）

- **不动**基线的抽帧六步法、12 类类别体系、知识库本地回填、双通道标注、mock、HTML 报告。
- **新增**：一个推理途径路由层（`inference.backend`）、视频时长校验、私有 VLM 适配器、端点探测命令、以及承载这些能力的配置段。
- **不改**任何既有默认行为：未配置新字段时，系统行为与基线一致（`inference.backend` 默认 `mock`，旧配置可直接加载）。

### 1.4 与当前代码现状的对照（避免误解为"从零开始"）

本节列出**已经存在**的能力，供架构师与工程师判断本次增量还差什么；未列出的能力一律视为**尚不存在**，不得在实现说明中默认其已具备。

- 已存在：`inference.backend` 四值路由（`mock` / `local_yolo` / `server_yolo` / `private_vlm`）；`private_vlm` 适配器（Ollama-native 请求体、顶层 `response` 字段、纯 base64 无 `data:` 前缀、`array`/`comma_joined` 两种 images 模式、`annotate_multi` 多图单请求）；Bearer Token 经环境变量注入且不落盘不写日志；`check_video_duration` 三策略（`warn`/`error`/`segment`）；`probe-inference` 三层端点探测；`extract` 阶段接入时长校验并把结果写入 `extracted/summary.json`。
- 已存在但需注意：`local_yolo` / `server_yolo` 途径**调用 `annotator` 时会直接抛错**（而非静默返回空结果），因为这两条途径不提供多模态能力。这是刻意的设计，不是缺陷。
- **尚不存在**（本次增量的待确认或后续项）：三途径的**级联/回退编排**（如 YOLO 初检 + VLM 复核）；**定时或事件触发**的抽帧调度；**自动按 1 分钟切段并逐段送模型**的端到端串联；YOLO 途径下的**知识库规则推断通道 B**。

## 2. 用户故事

1. **作为毕设作者**，我希望在一份配置里通过一个字段选择"用本机 YOLO / 用 lab-server YOLO / 用实验室私有 VLM"这三种解析途径，这样我在实验室、在宿舍、在答辩现场都能用同一套代码跑，不用改代码只改配置。
2. **作为毕设作者**，我希望三条途径的能力边界被系统显式告知——比如我误用 YOLO 途径去要隐患事件时，系统应直接告诉我"该途径不支持"，而不是悄悄给我一份空的隐患报告，这样我不会在论文里写出错误结论。
3. **作为毕设作者**，我希望系统在我投喂超过 1 分钟的视频时**立刻给出明确提示**（告诉我超了多少、上限是多少、建议怎么处理），而不是让我等了几十分钟才在某个 JSON 里发现结果不完整。
4. **作为毕设作者**，我希望把实验室给我的 Bearer Token 通过一个环境变量填进去就能用，token 不出现在配置文件、不出现在日志、不进 Git，这样我不用担心凭据泄露。
5. **作为毕设作者**，我希望送模型的图片自动完成 base64 编码与多图拼接，我不需要关心接口到底要数组还是逗号拼接的字符串。
6. **作为毕设作者**，我希望解析结果是结构化的（目标框一份、隐患事件一份，字段固定、编号必须命中知识库），这样我能直接喂给下游的训练、聚合与报告模块。
7. **作为现场安全员**，我希望系统在拒绝一段超长视频时，明确告诉我"这段视频的哪一部分可以先用"，而不是笼统地说一句"不支持"。
8. **作为答辩评委**，我希望看到一个不联网也能跑的演示路径（mock），并且系统会明确标注"这是演示数据"，这样我不会把演示结果误当成真实检测结果。

## 3. 需求池

优先级口径：**P0 = 必须实现（用户明确要求的 5 条 + 时长校验）**；P1 = 应当实现；P2 = 可以做。

### P0-1 三种解析途径的选择与切换（对应用户要求 1）

- **要求**：系统必须支持"本机 YOLO / lab-server YOLO / 实验室私有 VLM"三种解析途径，并通过**配置项**（而非改代码）在期间选择与切换。
- **要求**：配置项取值必须至少覆盖 `local_yolo` / `server_yolo` / `private_vlm`，并保留 `mock` 作为离线兜底。
- **要求**：切换途径后，**下游逻辑不得改变**——抽帧、聚合、训练、可视化、报告都消费同一套中间产物。
- **要求**：系统必须显式声明每条途径的**能力边界**，且在能力不匹配时**明确报错**而不是静默降级：
  - 途径一、途径二**只能**产出通道 A（目标框）；
  - 只有途径三（及 mock）能产出通道 B（隐患事件）；
  - 用途径一/二去索取隐患事件时，必须抛出可读错误，说明"缺什么能力、应该换哪条途径"。
- **要求**：必须提供一条**自检命令**，能打印当前途径、端点、模型名、凭据是否就位、时长策略，供用户在正式跑之前确认配置正确。
- **验收关联**：见第 5 节 A 组。

### P0-2 视频时长校验与明确提示（对应用户硬性限制）

- **要求**：在抽帧/送模型**之前**，必须先探测视频时长，并与"私有多模态模型 1 分钟上限"比较。
- **要求**：时长探测必须**优先使用容器精确时长**，探测失败时回退解析解码器输出；**两者都失败时视为"未知"并放行**（不得把"探测失败"误判为"超限"而误伤）。
- **要求**：超限时必须输出**明确、可读、含数字**的提示，至少包含：实际时长、上限、处置动作、建议做法。
- **要求**：超限处置策略必须可配置，且至少提供三种：
  - `warn`：告警但放行（并在结果中标记"结果可能不完整"）；
  - `error`：直接拒绝，附上"怎么改"的指引；
  - `segment`：不直接拒绝，而是**计算并给出建议的分段区间**（每段留安全余量），由用户决定是否分段执行。
- **要求**：校验结果必须**落盘可追溯**，写入抽帧摘要（含 `status` / `duration` / `limit` / `action` / 分段数 / 提示语 / 告警码），并汇总进告警列表。
- **要求**：校验必须**可被测试**——不得依赖真实视频才能验证（需支持注入探测结果）。
- **验收关联**：见第 5 节 B 组。

### P0-3 base64 编码与逗号拼接处理（对应用户要求 3）

- **要求**：送私有 VLM 前，图片必须转为 **base64** 编码。
- **要求**：编码结果**不带 `data:` URL 前缀**（按用户给出的请求体示例，`images` 里是纯 base64）。
- **要求**：必须支持**多图单请求**，且多图之间用**英文逗号**分隔。
- **要求**：由于用户给的"请求体示例（JSON 数组）"与"文字描述（逗号拼接的字符串）"存在歧义，系统必须**同时支持两种模式**并提供配置开关，默认取**与请求体示例一致**的那一种；切换模式不得需要改代码。
- **要求**：必须支持在一次请求里送多张图（例如把若干相邻关键帧打包送一次），以便模型跨帧推理。
- **要求**：编码逻辑必须是**可独立调用/可单测**的公开方法，不必真的连上端点才能验证编码正确性。
- **验收关联**：见第 5 节 C 组。

### P0-4 预留 Bearer Token 配置项（对应用户要求 4）

- **要求**：必须预留 Bearer Token 配置项，token 由用户后续自行填入即可生效，**不需要改代码**。
- **要求**：认证头格式必须为 `Authorization: Bearer <token>`，且 scheme 可配置（以适配可能的其他鉴权头）。
- **要求**：必须提供"要求凭据"开关：开启时缺 token 直接报错并给出填入指引；关闭时放行（适配不需要鉴权的部署）。
- **要求**：token **不得写入配置文件、不得写入日志、不得写入任何落盘产物**；日志中只允许出现"环境变量名"与"是否已就位"的布尔标记。
- **要求**：除标准 Bearer 外，必须预留**自定义请求头**与**自定义头来源（环境变量）**的配置位，以应对端点前置代理采用非标准鉴权头的情况。
- **验收关联**：见第 5 节 D 组。

### P0-5 输出结构化解析结果（对应用户要求 5）

- **要求**：每次解析必须输出**结构化结果**，且落盘位置固定、可被下游直接消费：
  - 通道 A：标准 YOLO 标签行（`label + 归一化 xyxy`），按帧一份；
  - 通道 B：隐患事件 JSON（`scene_type` / `hazards[]` / `overall_risk` / `recommendation`），按帧一份；
  - 合并记录：一行一帧的汇总文件；
  - 抽帧摘要：含总帧数、各步剔除数、最终关键帧数、所用途径、时长校验结果。
- **要求**：隐患事件的**必填字段必须完整**（`id` / `category` / `severity` / `norm_reference` / `action`），且 `hazards[].id` **必须 100% 命中知识库编号**，不允许模型编造编号。
- **要求**：模型只负责输出"隐患编号 + 证据"，其余字段由系统从知识库**本地回填**，保证与知识库强一致。
- **要求**：解析失败不得静默丢帧——必须把原始响应保留下来并把该帧送入人工复核队列。
- **要求**：解析结果中必须记录**本次使用的解析途径**，便于区分"目标框来自哪条途径"。
- **验收关联**：见第 5 节 E 组。

### P0-6 明确抽帧的触发方式与频率（对应用户要求 2）

- **要求**：必须提供**明确的抽帧入口命令**（单阶段只跑抽帧），并支持在全链路命令中把抽帧作为第一步自动执行。
- **要求**：抽帧频率必须**在文档与配置中显式定义**，并区分两层：
  - **第一层：粗采样频率（固定值）** —— 按配置的每秒采样帧数先把视频降采样，避免逐帧读满长视频；
  - **第二层：关键帧输出密度（内容自适应）** —— 由六步法逐步筛选决定，最终受"关键帧总数上限"与"相邻关键帧最小间隔"两个兜底约束封顶。
- **要求**：必须在文档中明确回答"频率到底是多少"这个问题——**粗采样是固定值，关键帧输出不是固定值，是内容自适应 + 双重封顶**。不得只写一个含糊的"自动抽帧"。
- **要求**：所有频率相关参数（采样频率、运动阈值、去重阈值、场景切换阈值、数量上限、最小间隔、强制保留类别）必须暴露到配置且有可用默认值。
- **要求**：抽帧必须支持**断点续跑**，并提供"强制全量重算"开关（长视频重跑成本高）。
- **验收关联**：见第 5 节 F 组。

### P0-7 配置扩展与示例项目

- **要求**：新增配置段必须承载：推理途径选择、时长上限与处置策略、分段长度、私有 VLM 端点与请求路径与模型名、images 传参模式、认证环境变量名与 scheme、自定义头、lab-server 连接参数。
- **要求**：**所有新增字段必须有默认值**，保证基线时期的旧配置文件仍可加载且行为不变。
- **要求**：必须提供**至少一个已配好私有 VLM 途径的示例项目**，用户填入 token 后可直接运行。
- **要求**：非法取值必须在校验阶段报错并说明合法取值（例如未知途径名、上限 ≤ 0、分段长度 > 上限）。
- **要求**：必须提供**端点出网策略**（默认只允许本机/内网；公网端点必须显式列入白名单），作为"防止改一个地址就把真实素材发到公网"的隐私护栏。本次新增的私有 VLM 端点为**公网 IP**，必须显式声明后才放行。
- **验收关联**：见第 5 节 G 组。

### P0-8 连通性探测（不发真实素材）

- **要求**：必须提供一条探测命令，在正式跑真实素材之前确认"端点通不通、token 对不对、请求体格式合不合"。
- **要求**：探测必须**分层**（至少：传输层可达性 → 无凭据探活/是否强制鉴权 → 可选的一次真实请求），且**任一层失败都返回结构化结果而不是抛异常**。
- **要求**：第三层（真实请求）默认**不执行**，需显式开启；即便开启，也只允许使用**本地合成图**，**不得涉及任何真实素材**。
- **要求**：探测必须能回答"凭据是否已就位"以及"当前还差什么才能发带认证的请求"。
- **验收关联**：见第 5 节 H 组。

### P1（应当实现）

- **P1-1 途径级联编排**：支持"YOLO 初检 → 把检出结果作为先验 → VLM 复核/判隐患"的两段式流程，以及"途径失败自动回退到下一条途径"的策略。**前置条件**：需用户先确认三途径是互斥还是级联（见第 4 节 Q1）。
- **P1-2 超长视频端到端分段执行**：在 `segment` 策略下，从"只给出建议区间"升级为"自动切段 → 逐段抽帧 → 逐段送模型 → 结果按时间轴合并"。
- **P1-3 YOLO 途径下的通道 B 规则推断**：途径一/二只出目标框，可用"目标框空间关联 + 知识库规则"推断 PPE 缺失类隐患，作为 VLM 不可用时的降级产出。**注意**：基线设计刻意不设 `no_helmet` 负类，此推断必须建立在"person 框与 helmet 框的关联"之上。
- **P1-4 途径自检并入统一诊断**：把途径自检、端点探测、时长策略、凭据状态合并进统一的环境诊断输出，一次命令看全。
- **P1-5 多帧单请求的批量策略**：定义"一次送几张帧"的打包规则（如按时间相邻度），并给出 token 预算与耗时的权衡说明。
- **P1-6 途径元数据贯穿产物**：把"本帧结果来自哪条途径、哪个模型、耗时多少"写入每帧结果，供论文做消融对比。

### P2（可以做）

- **P2-1 定时/事件触发的抽帧调度**：目前无调度器；可作为"无人值守监控"的延伸方向。
- **P2-2 途径质量与耗时对比实验**：三条途径在同一批关键帧上的输出一致性/耗时对比，作为论文实验章节。
- **P2-3 远程 YOLO 的带宽优化**：当前是逐张 `scp` 上传，可改为打包压缩后一次上传，降低长视频场景下的往返开销。
- **P2-4 凭据健康检查**：token 过期/失效时给出可区分的提示（区分"401/403 鉴权失败"与"网络不可达"）。

## 4. 待确认问题

以下问题**需要用户拍板**，未确认前不得在实现中替用户默认决定（已在代码中按保守默认实现的部分，也会在下方标明"当前默认"）。

### Q1 三条途径是"互斥选择"还是"级联回退"？（最高优先级）

- 用户的表述是"可在其间选择或切换"，"选择"与"切换"更像**互斥单选**；但工程上"YOLO 初检 + VLM 复核"是更常见的组合（YOLO 负责定位，VLM 负责语义判隐患）。
- **当前默认**：互斥单选（单一 `inference.backend` 字段）。
- 需要确认：
  - 是否允许**同时启用多条途径**（如本机 YOLO 出框 + 私有 VLM 判隐患）？
  - 是否需要**失败自动回退**（私有 VLM 不可达时自动降级到 YOLO）？若需要，回退后是否接受"只有目标框、没有隐患事件"的结果？
- 建议方案：**P0 保持互斥单选**（简单、可解释、答辩好讲），把级联作为 P1 扩展；如果用户确实需要级联，请明确"哪条途径负责出框、哪条负责判隐患"。

### Q2 抽帧的触发方式与频率（用户没有明说）

- 需要确认：
  - **触发方式**：只允许**手动执行命令**（调试友好），还是需要**全链路自动执行**（跑一次命令把抽帧→标注→报告全跑完），还是需要**定时/事件触发**（如每小时扫一次新视频）？
  - **频率**：粗采样是否接受"固定 1 帧/秒"？关键帧输出密度是否接受"内容自适应 + 上限 + 最小间隔"这个方案，而不是一个固定值？
- **当前默认（建议方案）**：
  - 触发方式：**手动单阶段命令**（只跑抽帧）+ **全链路命令**（抽帧作为第一步自动执行）；定时/事件触发**暂不实现**。
  - 频率：**两层频率**——第一层粗采样固定（默认 1 帧/秒，可配）；第二层关键帧输出为内容自适应，受"总数上限（默认 400）"与"相邻间隔下限（默认 2 秒）"双重封顶。
- 需要用户确认：这两个默认值是否符合他对"频率"的预期；如果他心里想的是"每 N 秒固定抽一帧"，请告知 N。

### Q3 1 分钟限制是"拒绝处理"还是"截取前 1 分钟"？

- **当前默认**：`warn`（告警但放行），并提供 `error`（拒绝）与 `segment`（给出分段建议）两个可选策略。
- 需要确认：
  - 用户希望**默认**是哪种？如果是"拒绝"，超限时是否希望系统**直接终止**（`error`），还是"拒绝但不终止、只跳过该视频"？
  - 是否需要"**只取前 1 分钟**"（截断处理）？当前实现**没有**这个策略，若需要请明确——它是"取前 1 分钟"还是"取最有可能有隐患的 1 分钟"（后者需要额外策略，成本更高）。
  - 1 分钟限制的**口径**是什么：是"输入视频本身的时长"，还是"一次请求送出的图片总时长/总数量"？（本系统实际送模型的是**关键帧图片**，不是视频流，因此"视频时长"与"送模型的数据量"并不是一回事。若限制的真实原因是显存/上下文预算，那么真正该约束的可能是"一次送几张图"。）
- **注意**：`segment` 策略当前**只给出建议区间，不自动执行分段**。如果需要端到端自动分段，请确认（对应 P1-2）。

### Q4 本机 YOLO 与 lab-server YOLO 的差异

- 需要确认：
  - 两条 YOLO 途径是否使用**同一份权重文件**？还是服务器上有**不同权重/不同训练版本**？
  - 两者的**类别体系是否一致**？服务器上的模型是否也是那 12 类施工类别？如果服务器上跑的是通用 COCO 权重（80 类），则其输出**无法直接映射**到本项目的类别体系，需要额外处理。
  - 是否需要保证"同一张图在本机与服务器上结果一致"（用于论文做一致性对比）？
- **当前默认**：本机使用本地配置的检测权重，服务器使用独立的远程权重配置；**两者未做任何一致性校验**。服务器未配置权重时回退为通用小模型权重，此时类别体系**大概率不匹配**——请务必确认服务器上的实际权重。

### Q5 `images` 到底传数组还是逗号拼接的字符串？

- 用户给的**请求体示例**是 JSON 数组 `"images": ["base64编码1", "base64编码2"]`；**文字描述**是"多张图片之间用英文逗号隔开"（更像单个字符串）。二者不一致。
- **当前默认**：数组模式（对齐请求体示例），同时支持逗号拼接模式，切换只需改配置。
- 需要确认：服务端实际接受哪种？建议在拿到 token 后先用探测命令的"真实请求"层各试一次再定。

### Q6 Bearer Token 的具体传递方式

- 探测发现：端点无凭据访问返回的 **403 页面来自前置代理（nginx）**，说明鉴权**可能发生在代理层而非应用层**。
- 需要确认：
  - 鉴权头是否就是标准的 `Authorization: Bearer <token>`？
  - 如果是代理层的自定义鉴权头（如 `X-Auth-Token` 之类），请提供头名。
  - token 的**有效期**是多久？是否需要刷新机制？
- **当前默认**：标准 Bearer；已预留自定义头与"头值来自哪个环境变量"的配置位，可在不改代码的前提下适配。

### Q7 lab-server 的连接参数是否正确

- **当前默认**：主机名 `lab-server`；远程工作目录与激活脚本路径已按既有部署预填。
- 需要确认：主机名是否可直接解析？**ssh 免密**是否已配好？远程**是否已安装 yolo 命令行**？激活脚本路径是否正确？远程磁盘是否有足够空间（上传关键帧会占用远程空间）？

### Q8 真实运行授权

- 代码已实现并有单元测试覆盖，但**尚未对任何真实素材实际调用过**这三条途径中的任何一条。
- 需要用户明确授权后，才能用真实素材做首次端到端验证。首次验证建议先用**合成图**跑通（不涉及真实素材），再换真实素材。

### Q9 端点白名单与地址稳定性

- 新增的私有 VLM 端点是**公网 IP**，必须显式列入出网白名单才放行（这是刻意的隐私护栏）。
- 需要确认：该 IP/端口是否**长期固定**？如果会变，白名单需要同步维护；是否需要提供"临时放行"的运维口径？

### Q10 时长探测失败时的行为是否可接受

- **当前默认**：探测失败（既拿不到容器时长、也解析不出解码器输出）时，**记为"未知"并放行**，只留一条告警。
- 需要确认：这是否可接受？还是希望"探测失败即拒绝"（更保守，但可能误伤能正常处理的视频）？

### Q11 途径三的并发与耗时预期

- 30B 带 thinking 的模型单帧很慢。需要确认：服务端**并发能力**如何？是否允许并发请求？单帧**预期耗时**是多少？是否需要为超时与重试设置更宽松的默认值？

## 5. 验收标准

所有条目必须**可量化、可测试**；标注"合成图/替身"的条目不得依赖真实素材或真实端点。

### A 组：途径选择与切换（对应 P0-1）

- 三种途径（+ mock）均能被正确构造，且自检输出包含：当前途径、可选途径清单、端点、模型名、凭据是否就位、时长策略。
- 未知途径名**必须报错**，且错误信息列出全部合法取值。
- 用途径一/途径二索取隐患事件（通道 B）时，**必须抛出可读错误**，错误信息包含"该途径不提供多模态能力"与"应改用哪条途径"；**不得静默返回空隐患列表**。
- 切换途径只需修改配置一个字段，**不改任何代码**；切换后下游（抽帧/聚合/训练/可视化）产出结构不变。
- 三条途径的产物中均记录"本次使用的途径"标识。

### B 组：视频时长校验（对应 P0-2）

- 边界用例必须全部通过（可用替身注入时长，不依赖真实视频）：
  - 时长明显小于上限 → 判定通过、放行；
  - 时长**恰好等于**上限 → 判定通过、放行（边界含在内）；
  - 时长超限 + `warn` → 告警放行，结果中带"结果可能不完整"标记；
  - 时长超限 + `error` → 抛出明确错误，错误信息包含实际时长、上限、以及"如何改为其他策略"；
  - 时长超限 + `segment` → **不拒绝**，给出分段数与具体区间建议，且每段长度 ≤ 配置的分段长度、分段长度 < 上限；
  - 时长探测失败 → 判定为"未知"、放行、留告警，**不得**误判为超限。
- 校验结果**必须落盘**：抽帧摘要中包含时长、上限、状态、处置动作、分段数、提示语，且告警码进入汇总告警列表。
- 提示语必须**含具体数字**（实际时长与上限），不得只有"视频过长"这类无信息量的文案。

### C 组：base64 编码与多图拼接（对应 P0-3）

- 数组模式：`images` 为列表，每个元素是**纯 base64**，**不含 `data:` 前缀**，且每段可被独立解码回原始字节。
- 逗号拼接模式：`images` 为**单个字符串**，多图之间以**英文逗号**分隔，按逗号切分后每段可独立解码。
- 请求体字段集合必须为 `model / prompt / options / stream / images`，**不得包含 `messages`**（与用户给的契约一致）。
- 多图单请求：一次请求可携带 N 张图（N ≥ 2），且请求体中图片数量与入参一致。
- 编码逻辑可在**不连端点**的情况下被直接调用并断言。

### D 组：Bearer Token（对应 P0-4）

- 设置了 token 环境变量时，请求头包含 `Authorization: Bearer <token>`。
- 未设置 token 且"要求凭据"开启时，**报错**，错误信息包含"应设置哪个环境变量"。
- 未设置 token 且"要求凭据"关闭时，放行（请求头不含认证）。
- **安全断言**：在配置文件、日志输出、落盘产物（含请求预览）中**检索不到 token 明文**；请求预览中只出现环境变量名与"是否已就位"的布尔值。
- 自定义头配置生效：当配置了自定义头名与环境变量时，该头被注入请求，且其值同样不落盘。

### E 组：结构化解析结果（对应 P0-5）

- 每个成功解析的关键帧同时存在：通道 A 的标签文件、通道 B 的隐患事件文件、以及合并记录中的一行。
- 隐患事件 JSON 必填字段完整率 **≥ 95%**；`hazards[].id` 命中知识库编号的比例 **= 100%**。
- `category / norm_reference / action` 三个字段由本地知识库回填，且与知识库逐条一致（抽样比对零差异）。
- 解析失败的帧：原始响应**被保留**、该帧**进入复核队列**，且失败帧数 + 成功帧数 = 总处理帧数（**零静默丢失**）。
- 抽帧摘要含：总帧数、各步剔除数、最终关键帧数、所用途径、时长校验结果。

### F 组：抽帧触发与频率（对应 P0-6）

- 存在**单阶段抽帧命令**，执行后产出关键帧、候选记录与抽帧摘要三样产物。
- 存在**全链路命令**，执行后抽帧作为第一步自动完成。
- 配置中的频率参数全部生效：修改采样频率后，抽样帧数按比例变化；修改关键帧上限后，最终关键帧数不超过该上限；修改最小间隔后，相邻关键帧时间差不小于该值。
- 抽帧摘要必须能回答"总共多少帧、采样多少帧、运动剔除多少、去重剔除多少、最终多少"。
- 断点续跑：输入与抽帧配置均未变化时重跑，**复用已有结果**（不重算）；使用"强制全量重算"开关时，全部重算。
- 在长视频等效输入上，最终关键帧数**不超过配置上限**（默认 400）。

### G 组：配置与示例（对应 P0-7）

- 基线时期的旧配置文件**可直接加载且不报错**，行为与基线一致。
- 新增字段均有默认值；逐一删除任一新增字段后加载仍成功。
- 非法取值触发校验错误，错误信息包含合法取值清单：未知途径名；时长上限 ≤ 0；分段长度 > 时长上限；images 模式非法值。
- 示例项目可直接加载；其中私有 VLM 端点因是公网地址，**必须显式列入白名单才放行**；若移除白名单条目，加载**必须报错**并说明这是隐私护栏及如何显式声明。
- 默认出网策略下，未列入白名单的公网端点**一律被拒绝**。

### H 组：连通性探测（对应 P0-8）

- 探测命令默认**只执行**传输层可达性与无凭据探活，**不发送任何业务数据**。
- 传输层探测能给出"可达/不可达"与耗时；无凭据探测能给出状态码，并把"强制鉴权"识别为**正常信号**而非故障。
- 第三层真实请求默认**不执行**；未设置 token 时即便开启也**不发送**，并明确告知"缺什么"。
- 探测使用的图片必须是**本地合成图**；探测过程中**不得读取任何真实素材**（可通过"探测产物中不含真实素材路径"来断言）。
- 任一层失败时命令**不崩溃**，返回结构化结果与一句可读结论。

### I 组：回归（不破坏基线）

- 基线既有测试全部通过。
- mock 全链路命令**退出码为 0**，产出与基线一致。
- 未配置任何新增字段时，系统默认行为与基线一致（`inference.backend` 默认 `mock`）。
