# 模块设计与项目推进方案：自动抽帧与标注数据集构建

> 编制时间：2026-09-16
> 模块代号：`auto_dataset`（自动抽帧与标注数据集构建）
> 编制依据：对现有 `hazard_annotation/` 的代码级核实 + `GAP-生产可用性差距评估.md`
> 定位：这是整个闭环的**数据供给端**，也是当前唯一"必做且能独立交付"的模块

---

## 第一部分：模块设计

## 一、模块定位

**一句话**：把「一段视频」变成「一份可直接投喂 YOLO 训练、且可追溯、可复现、可验收的标注数据集」。

**在整体架构中的位置**：

```
视频源/相机 ──▶ 【auto_dataset】──▶ 训练 ──▶ 评估 ──▶ 门禁 ──▶ 部署
                      │                                      │
                      └────────── 回流样本 ◀──────────────────┘
```

**它负责**：抽帧、标注、数据集组装、数据质量校验
**它不负责**：模型训练、推理部署、监控告警（那是下游模块的事）

**为什么这个模块应该优先做**：

1. **它是数据供给端，决定下游一切的上限。** 抽帧丢掉的信息，后续任何模型都补不回来。
2. **它是当前完成度最高的一段。** 抽帧、标注、数据集生成都已跑通，180 个测试全绿——在现有基础上产品化，比从零做推理服务划算得多。
3. **它可以独立交付、独立验收。** 不依赖 `base_url`（可用 mock 或本地模型）、不依赖推理服务。
4. **它能顺手解决评估闭环的前置条件。** 见下文「一个关键设计决策」。

## 二、功能清单

### 第 1 层：帧获取（Frame Acquisition）

- 新增：RTSP / 相机流接入（生产必需，但可放到 S4 阶段）
- 设计要点：源抽象成 `KeyframeSource`，新增源类型不改下游

**F1.2 六步关键帧提取** —— 已有

- 实现：`hazard_annotation/keyframes.py`
- 参数全部暴露到配置的 `keyframe` 段

**F1.3 抽帧断点续跑** —— **新增（重要缺口）**
- 现状：`extraction.py` 只有 2 个函数，**没有 resume 逻辑**（`annotation.py` 有，抽帧没有）
- 需求：长视频抽帧中断后重跑，已完成的分片不重复计算

**F1.4 抽帧质量报告** —— 已有，需增强

**F2.1 通道 A 目标框标注** —— 已有

**F2.2 通道 B 隐患事件标注** —— 已有

- 知识库 58 条，`norm_ref` 覆盖率已 100%

**F2.3 知识库压缩注入 + 场景路由** —— 已有
- 按场景（S1 吊装 / S2 高处）只注入对应清单，受 `kb_max_chars` 约束

**F2.4 thinking 稳健解析** —— 已有
- 剥离思维链 → 取最后一个平衡 JSON → 有界修复

**F2.5 严禁静默丢帧** —— 已有（这是好设计，要守住）
- 解析失败进复核队列，保留原始响应到 `raw_responses/`

**F2.6 并发与断点续跑** —— 已有
- `ThreadPoolExecutor` + 已完成帧跳过（`annotation.py:246-256`）

**F2.7 通道一致性校验** —— **新增（PRD P1-3）**

**F2.8 复核工作流工具** —— **新增（重要缺口）**
- 现状：`review_queue.jsonl` 生成后要人直接读 JSON
- 需求：本地 Web 复核页（逐帧确认/修正/批量操作），复用已有的自包含 HTML 技术路线
- 作用：**人工成本直接决定闭环能不能转起来**

### 第 3 层：数据集组装（Dataset Assembly）

**F3.1 训练/验证/测试切分** —— 已有
- `train_split / val_split / test_split` + `seed`

**F3.2 固定评估集（holdout）** —— **新增（关键设计，见第五节）**
- 现状：`dataset_version = f"v{timestamp_token()}"`，每轮重新随机切分 → **跨轮指标不可比**

**F3.3 数据分层与均衡采样** —— **新增**

**F3.5 数据集卡片（dataset card）** —— **新增**

### 第 4 层：可观测与运维

## 三、输入契约

**必需输入**

- 视频文件路径（`video.video_path`）或图片目录（`input.frames_dir`）—— 二者至少其一
- 配置文件（`examples/hazard_project/config/project.json` 或同类）
- 隐患知识库（`hazard-detection/knowledge_base.json`，58 条）
- 提示词模板（`assets/prompts/*.md`）

**可选输入**

- YOLO 初检权重（`yolo.detector_weights`）—— 缺省时降级为 sidecar 或 mock
- 模型服务地址（`qwen.base_url`）—— mock 模式可不需要
- 上一轮的数据集版本（用于增量构建与 diff）

**关键配置项（`keyframe` 段）**

```
sample_fps            采样帧率，默认 1.0
analysis_width        分析帧宽度，默认 160（决定运动检测与去重精度）
motion_min_ratio      运动占比下限，默认 0.002
pixel_delta_threshold 像素差阈值，默认 25
dedup_hamming_threshold 去重汉明距离阈值，默认 4
phash_size            感知哈希尺寸，默认 8
scene_change_threshold 场景切换阈值，默认 0.4
scene_detect_mode     场景检测后端，ffmpeg 或 histogram
max_keyframes         关键帧上限，默认 400
min_gap_seconds       最小间隔秒数，默认 2.0
force_keep_labels     强制保留的类别，默认 8 类
```

## 五、验收标准

### 抽帧层

- 投喂 1 小时 @25fps 视频，关键帧落在 **300~500 张**（压缩比 ≥180:1）
- 人工抽检**漏帧率 ≤5%**（真实存在隐患动作的时段被整体丢弃的比例）
- `summary.json` 完整包含 9 项计数，且满足：`final_keyframes = len(candidates)`
- **断点续跑可用**：抽帧中断后重跑，已完成分片不重复计算（可用耗时对比验证）
- 所有阈值改配置即生效，无需改代码

### 标注层

- 通道 B 必填字段完整率 **≥95%**（当前已达标）
- 隐患 `id` **100% 落在知识库 58 条内**，不允许编造编号
- 解析失败帧 **0 静默丢弃**：全部进复核队列且原始响应被保留
- `combined_call=true` 时单帧只发生 **1 次模型请求**（可通过日志验证）
- 并发与断点续跑可用；已完成帧跳过
- 通道一致性校验能捕获"报未戴帽但检出 helmet 框"的矛盾并进队列

### 数据集层

- `data.yaml` 的 `names` 与配置 12 类**逐项一致**
- 数据集校验 **0 错误**（坐标范围、类别越界、空标签、配对完整性）
- **holdout 集跨轮次哈希不变**（连续两轮生成，哈希一致）
- 每个样本可追溯：`manifest.json` 含 image_path / label_path / hazard_ids
- 类别直方图无"0 样本类别"，或对缺失类别显式告警
- 数据集卡片包含抽帧参数快照与知识库版本

### 端到端

- 在无视频、无模型的干净机器上，**一条命令跑通全链路且零报错**（已有能力，需保持）
- 输出中 mock / 真实模式标识正确，**mock 指标不得被误认为真实结果**

## 六、一个关键设计决策：让本模块同时产出评估集

这是本次设计里**最值得强调的一点**。

**问题**：`GAP` 评估里指出，项目最尴尬的地方是「系统很完整，但核心价值（隐患识别）没有数字」。要算隐患识别的 P/R/F1，必须有「哪一帧真的有什么隐患」的黄金标注——而目前完全没有。

**洞察**：这个黄金标注集，**和训练数据集是同一批数据、同一条产线**。

**方案**：本模块在生成训练集的同时，**划出一个固定不动的 holdout 集并做完整人工校验**（即黄金标注）。于是：

- 训练集 → 喂给 S3 的训练闭环
- holdout（黄金标注）→ 喂给 S2 的评估闭环，算 P/R/F1

**收益**：一次投入，同时解决「数据供给」和「评估基线」两个问题。这是把 S1 和 S2 合并推进的最佳切点。

**代价**：需要对 holdout 做人工精标（量不用大，200~300 帧即可，但必须准）。

## 八、优先级排序

### 按目标分流

**如果目标是毕设 / 论文**
S0 → **S1** → **S2** → S3

理由：答辩最需要的是"有数据、有指标、有闭环叙事"。S1 给数据，S2 给数字，S3 给闭环的故事。S4/S5 属于工程落地，答辩加分有限。

**如果目标是产线上线**
S0 → **S1** → **S2** → **S4** → **S3** → **S5**

理由：S2 是质量前提（没有评估就不知道模型行不行），S4 让系统先跑起来产生价值，S3 让模型自己迭代，S5 才是长期运维。

**无论哪个目标，S1 都是第一优先级** —— 因为它是唯一的"没有它，下游全都做不了"的模块。

### 全局优先级排序（按"不做会怎样"）

**P0（不做就卡死）**
1. S1 固定评估集 —— 没有它，跨轮指标永远不可比
2. S1 抽帧断点续跑 —— 没有它，长视频任务不可用
3. S2 隐患量化评估 —— 没有它，核心价值无法度量
4. S3 回流消费器 —— 没有它，闭环不闭
5. S4 推理服务 —— 没有它，检测落不了地
6. S5 监控告警 —— 没有它，生产裸奔

**P1（影响效率与可用性）**
7. S1 复核工具、数据集校验、分层采样
8. S3 质量门禁、调度
9. S4 实时采集、性能基准
10. `base_url` 本地性护栏（安全，独立于阶段，**建议随时补**）

**P2（优化与规模化）**
11. S5 灰度回滚、多机位、漂移检测
12. 实验管理、超参搜索、主动学习

**关键依赖约束**

- **S3 的质量门禁依赖 S2 的评估能力**：没有评估就没法设阈值
- **S4 依赖 S1→S3 产出的权重**：没有训练好的模型，推理服务没东西可服务
- **S1 不依赖任何未完成项** —— 这是它能作为起点的根本原因
