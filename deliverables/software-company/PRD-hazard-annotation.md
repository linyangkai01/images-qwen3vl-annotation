# 工业施工安全隐患自动标注系统 — 产品需求文档（PRD）

## 0. 项目信息

- **文档类型**：简单 PRD（毕设项目，不做竞品分析）
- **文档语言**：中文
- **项目名称**：`hazard_annotation`（工业施工安全隐患自动标注系统）
- **技术栈（默认）**：Python 标准库为主 + 复用现有 `traffic_cv_closed_loop` 闭环骨架；自部署 qwen3-vl 推理走 OpenAI 兼容接口；视频解码/YOLO 走外部 CLI（ffmpeg / ultralytics）；可视化输出为自包含静态 HTML
- **原始需求复述**：作者要基于现有开源工程做毕设改进。现有工程有两块互不相连的基础——`traffic_cv_closed_loop/`（交通场景的 Qwen→YOLO 闭环训练骨架，管"目标框"）和 `hazard-detection/`（58 个施工隐患点知识库，管"隐患语义"）。两者之间没有任何代码连接，且类别体系、Prompt、抽帧策略全是交通场景的。本项目的核心工作，是**用一套施工安全语义把两条通道接起来**：通道 A 用 YOLO 检测施工安全对象并产出可量化指标，通道 B 用自部署 qwen3-vl 产出隐患事件报告，两通道共用一套关键帧与知识库，并形成闭环回流。
- **硬约束**：用户因安全隐私原因**不能提供原视频**，因此系统必须交付**可在用户本机直接运行的代码**，由用户自行投喂视频；开发与答辩阶段必须能用 mock/demo 数据把整条链路跑通。

## 1. 产品目标

**一句话定位**：把一段 1 小时的单路固定机位施工监控视频，自动压缩为数百张关键帧，并同时输出"目标框标签"（可训练 YOLO）与"隐患事件报告"（可读、可追责、带规范依据）的双通道标注系统，且视频帧只发往用户自有的模型服务、全程不经第三方 API。

**可衡量目标**：

1. **关键帧压缩比**：1 小时（约 9 万帧 @25fps）视频 → 输出关键帧控制在 **300~500 张**（压缩比 ≥ 180:1），且通过抽样人工校验，**漏帧率 ≤ 5%**（即真实存在隐患动作的时段被整体丢弃的比例）。
2. **通道 A 可量化指标**：在自建施工对象数据集上完成 YOLO 训练，产出 **mAP50、Precision、Recall** 三项指标，mAP50 在演示数据集上 **≥ 0.60**（毕设答辩可展示的训练曲线与混淆矩阵）。
3. **通道 B 结构合规率**：对关键帧输出的隐患事件 JSON，**字段完整率 ≥ 95%**（必填字段 id / category / severity / norm_reference / action 齐全），且 `hazards[].id` **100% 落在知识库 58 个编号内**（不允许模型编造编号）。
4. **私有化与数据合规**：主通道由**用户私有部署的** `qwen3-vl:30b-a3b-thinking-q8_0` 完成，**视频帧只发往用户自有的模型服务（自部署的 `base_url`），不经任何第三方 API**；云端百炼通道默认关闭，仅在配置显式切换时才可被调用。
5. **可复现性**：在无视频、无模型的干净机器上，仅执行一条命令即可用 mock 数据跑通"抽帧→标注→隐患报告→数据集→训练→可视化"全链路，**端到端零报错**（答辩演示的兜底路径）。

## 3. 需求池

### P0（必须实现，毕设主线）

#### P0-1 智能关键帧提取（1 小时视频 → 数百关键帧）

- **背景**：现有 `pipeline/extraction.py` 只处理**已经切好的图片目录**，按 `frame_step` 等间隔抽样，不读视频、不做运动检测、不做去重。1 小时 @25fps ≈ 90,000 帧，等间隔抽样仍会保留大量静止/无人冗余帧。
- **要求**：新增"视频 → 关键帧"预处理能力，串行执行以下策略，最终产出受控数量的关键帧：
  1. **粗采样**：调用 ffmpeg（外部 CLI，与现有 yolo CLI 调用方式一致）按 `sample_fps`（默认 1 fps）解码并等比缩放，避免逐帧读满 9 万帧。
  2. **运动检测**：基于相邻帧差分/背景建模计算运动像素占比，占比低于 `motion_min_ratio` 的帧判定为静止，剔除。
  3. **感知去重**：对保留帧计算感知哈希（pHash/直方图），相邻帧汉明距离低于 `dedup_hamming_threshold` 时只保留代表帧。
  4. **场景切换强制保留**：直方图突变超过 `scene_change_threshold` 的帧强制作为关键帧（防止去重把"切换瞬间"吃掉）。
  5. **目标驱动保底**：对 YOLO 初检命中关键对象（人员/吊钩/梯子等）的帧强制保留，保证隐患帧不被去重误删。
  6. **上限裁剪与最小间隔**：总关键帧不超过 `max_keyframes`（默认 400）；相邻关键帧时间间隔不小于 `min_gap_seconds`（默认 2s），避免同一动作刷屏。
- **可调参数**：以上所有阈值均须暴露到配置文件（见 P0-8），默认值可直接跑通。
- **复用**：输出目录结构沿用现有 `input/frames/<source_id>/`，使后续 `extraction.py` 无需大改即可消费。

#### P0-2 施工安全对象类别体系设计（替代交通类别）

- **背景**：现有 `labels` 为交通场景（person, car, bus, truck, motorcycle, traffic_light），必须整体替换。
- **要求**：设计一套面向"吊装 + 高处"两场景的施工安全对象类别，写入配置 `labels`。**已定版为 12 类**（经架构评审，从初版 17 类建议收敛）：
  - **人员与 PPE**：`person`（人员）、`helmet`（安全帽）、`vest`（反光背心/警示服）、`harness`（安全带/安全绳）
  - **吊装要素**：`hook`（吊钩）、`rigging`（吊索具，统称吊链/吊带/钢丝绳）、`overhead_crane`（行车/龙门吊/起重机）、`load`（被吊物品）
  - **高处作业要素**：`ladder`（梯子）、`scaffold`（脚手架/作业平台，含移动脚手架）、`guardrail`（防护栏）
  - **通用**：`pallet`（托盘/卡板）
- **收敛理由（相对初版 17 类建议）**：
  - `chain` / `sling` / `wire_rope` 三者视觉特征相近、单类样本量小 → **合并为 `rigging`**，降低类别碎片化与漏标成本。
  - **删除 `spreader_beam`（平衡梁）、`hopper`（料斗）**：样本极少且与 `load` 高度混淆，其违规判定（如 D-3-3 未用平衡梁、D-3-1 散件未用料斗）交由通道 B 结合知识库推断，不必占用检测类别。
  - **`mobile_scaffold` 并入 `scaffold`**：单路固定机位下移动脚手架与普通脚手架难以稳定区分，合并后可保证每类样本量。
- **设计说明（重要）**：**不设置** `no_helmet` 这类"缺失态"类别。PPE 缺失（如 D-5-1 未戴安全帽、G-2-2 未系安全带）由"person 框与 helmet/harness 框的空间关联 + 知识库规则"推断，而非让检测器学一个语义含糊的负类。这样通道 A 只需检测"实体"，通道 B 负责"是否违规"。
- **要求**：类别清单已定版 12 类，后续如需增减须提供"新增类别的成本说明"（改 labels + 补标注 + 重训）。

#### P0-3 隐患知识库注入（把 knowledge_base.json 接进 Qwen Prompt）

- **背景**：`knowledge_base.json` 约 30KB、58 个隐患点（S1 吊装 27 条 + S2 高处 30 条 + S3 通用 1 条）。**不能全量硬塞**进每帧 Prompt——30B 带 thinking 模型上下文与 token 预算都吃紧，且会稀释注意力、降低结构化输出稳定性。
  - **数据口径说明**：知识库 `meta.total_hazards` 字段原写 53（陈旧错误），**现已修正为 58**；实际隐患条数以解析结果 **58 条**为准（代码与测试均已按 58 条实现）。
- **要求**：实现"分场景 + 压缩注入"策略：
  1. **场景路由**：先用一个轻量 Prompt 让模型判断当前关键帧属于"吊装作业 / 高处作业 / 两者兼有 / 无"，据此**只注入对应场景**的隐患清单（S1 或 S2）。
  2. **字段裁剪**：注入时只保留对识别有用的字段——`id + name + visual_cues + severity`，**丢弃** `description / action / norm_ref`（这三项由系统在收到模型返回的 `id` 后，从知识库**本地回填**，既省 token 又杜绝模型编造规范号）。
  3. **规则附加**：当路由为吊装场景时，额外注入 `ten_no_lift`（10 条）与 `crane_six_forbidden`（6 条）规则。
  4. **Token 预算**：新增 `kb_max_chars` 参数限制注入文本长度，超限时按 `severity` 从高到低截断并告警。
  5. **缓存**：压缩后的场景知识片段在启动时生成一次并缓存，避免每帧重复序列化。
- **回填**：模型只输出隐患 `id` 与 `evidence`，系统据此从知识库补全 `category / norm_reference / action`，保证字段完整且与知识库强一致（对齐 P0-4 目标 3）。

#### P0-4 双通道标注

- **要求**：对每个关键帧，同时产出两路结果：
  - **通道 A（目标框）**：输出 `objects[]`（label + 归一化 xyxy bbox + confidence + notes），转成 YOLO `*.txt` 标签行；沿用现有 `pipeline/annotation.py` 的 YOLO↔Qwen 比对逻辑（added/removed/adjusted 统计）与人工复核队列。
  - **通道 B（隐患事件）**：输出隐患事件 JSON，字段沿用知识库既定格式：
    - `scene_type`
    - `hazards[]`：`id / category / description / confidence / evidence / severity / norm_reference`
    - `ten_no_lift_violations[]`、`crane_six_forbidden_violations[]`
    - `overall_risk`（critical/high/medium/low/none）
    - `recommendation`
- **单次推理合并（性能关键）**：由于 30B 带 thinking 单帧很慢，**默认将通道 A 与通道 B 合并为一次 Qwen 调用**，返回 `{ "objects": [...], "hazard_report": {...} }` 的组合 JSON；提供 `qwen.combined_call=false` 开关，可回退为两次独立调用（便于调试与消融实验）。
- **先验注入**：把通道 A 的 YOLO 初检结果作为 `prior_detections` 注入通道 B 的 Prompt（复用现有 `prompting.py` 的占位符机制），降低模型"看不到小目标"导致的漏报。
- **输出落盘**：通道 B 结果写入 `workspace/hazards/<relative_path>.json`，并汇总为 `workspace/hazards/report.json`（按时间轴 + 等级聚合）。
- **验收现状（已达标）**：知识库 58 条隐患的 `norm_ref` 已**全部补全**（覆盖率 100%，原为 11/58 = 18.97%）。
  通道 B 必填字段完整率随之从 **27.27% 提升至 ≥ 95%**，`PrdAcceptanceFindingsTest` 全部通过。
  补录工具：`scripts/fill_norm_ref.py`；候选依据清单：`deliverables/software-company/norm_ref-待补清单-候选建议.md`。

#### P0-5 自部署 qwen3-vl 接入（OpenAI 兼容 + thinking 稳健解析）

- **背景**：主通道为**用户私有部署**的 `qwen3-vl:30b-a3b-thinking-q8_0`（Ollama/vLLM 风格，部署在用户自有服务器上，**非第三方 API、也非本机 localhost**），暴露 OpenAI 兼容接口。现有 `adapters/qwen.py` 已实现 `OpenAICompatibleQwenAnnotator`（base64 内联图、重试、`response_format=json_object`），可直接复用；但**带 thinking 的输出会先吐思维链再吐 JSON**，现有 `_extract_json_from_text` 取"第一个像 JSON 的片段"，极易误抓思维链里的花括号。
- **要求**：
  1. 新增 provider 取值（如 `local_openai` 或复用 `openai_compatible`），`base_url` 读取配置 `qwen.base_url`（指向用户自部署服务，实际地址待定，见第 6 节）、`model=qwen3-vl:30b-a3b-thinking-q8_0`、`require_api_key` 按部署要求可配。
  2. **thinking 处理**：优先通过请求参数关闭/隔离思维链（如 `extra_body` 传 `think:false` 或 chat_template_kwargs）；无法关闭时，实现"剥离思维链段 + 取**最后一个**平衡 JSON 对象"的稳健解析。
  3. **JSON 修复**：解析失败时做有限修复（去除尾逗号、单引号转双引号、截断恢复），仍失败则记入复核队列并保留原始响应，不得静默丢帧。
  4. **性能与超时**：针对单帧慢，`timeout_seconds` 默认放大（≥180s），支持失败重试与并发度参数（可选）。
  5. **探活**：复用/扩展 `diagnostics.py` 的 `probe-qwen`，输出自部署服务连通性、模型名、单帧耗时。
- **备选通道**：保留阿里云百炼 compatible-mode 为**可选**，仅当配置显式切换 provider 时才启用，默认关闭。

#### P0-6 数据集生成 + YOLO 训练 + 困难样本回流（复用现有闭环）

- **要求**：直接复用 `pipeline/training.py` 的能力，做施工场景适配：
  1. 数据集切分（train/val/test）→ 生成 `data.yaml`（`names` 使用 P0-2 新类别）→ 调用 YOLO 训练 → 产出指标。
  2. **回流扩展**：现有"困难样本"仅来自通道 A 的复核队列；需**新增通道 B 回流**——把"检出隐患（尤其 critical/high）"的关键帧也标记为困难样本/高价值样本，优先进入下一轮训练与复核。
  3. 训练报告需包含：mAP50、P、R、混淆矩阵、类别直方图、困难样本清单、下一轮任务建议（沿用现有 `next_cycle_tasks.md`）。
  4. **验收指标**：报告中的 mAP50/P/R 必须可被读取并展示到可视化页。

#### P0-7 mock 模式（无视频、无模型也能跑通全链路）

- **背景**：硬约束要求开发/答辩可在无真实素材环境运行。
- **要求**：
  1. 提供 `provider=mock`，复用现有 `MockQwenAnnotator` 的 sidecar 机制（`*.detections.json` / `*.qwen.json`），并**新增隐患 sidecar**（`*.hazard.json`），使通道 B 也能离线产出。
  2. 提供一套 demo 资产：合成的关键帧图片（可复用现有 `.ppm` 方式）+ 对应的对象/隐患 sidecar，覆盖"吊装多隐患""高处梯具违规""无隐患"三类典型场景（对齐 `detection_examples.md` 示例）。
  3. 提供**一键命令**（如 `1.py --stage all --mock` 或独立 `run_demo`），在干净机器上零配置跑通全链路。
  4. mock 与真实模式的差异必须在文档与输出中显式标注（避免答辩时被误认为真实结果）。

### P1（应当实现）

- **P1-1 隐患时间聚合与持续性判定**：把逐帧隐患事件按 `id` 沿时间轴聚合，标注"首次出现帧/持续时段"，输出"持续性隐患"列表（对齐 `prompt_templates.md` 场景 C 的 `persistent_hazards`）。
- **P1-2 整改前后对比视图**：支持选定两张关键帧做"整改前/后"对比，输出已消除/未消除/新增隐患与整改率（对齐 `detection_examples.md` 示例 4）。
- **P1-3 通道一致性校验**：用通道 A 的检测结果交叉校验通道 B——例如模型报"未戴安全帽"但通道 A 检出了 helmet 框时，标记为可疑并进复核队列，降低幻觉。
- **P1-4 批量并发与断点续跑**：标注阶段支持并发与失败重跑（30B 单帧慢，长视频需要容错），已完成的帧跳过。
- **P1-5 指标导出**：把 mAP50/P/R、隐患等级分布、压缩比等汇总为一份可放进论文的指标文件。

### P2（锦上添花）

- **P2-1 多机位/多视频批处理**：从单路扩展到多路视频汇总。
- **P2-2 隐患编号自动映射到整改单模板**：导出可打印的整改通知单（PDF/Word）。
- **P2-3 云端通道消融对比**：自部署 vs 百炼的质量/耗时对比实验，作为论文实验章节。
- **P2-4 主动学习采样**：按不确定度挑选下一轮送标帧。

## 5. 验收标准

- **P0-1 关键帧提取**：投喂 1 小时视频（或等效长序列）后，产出关键帧数落在 300~500；生成 `summary.json` 记录"总帧数/采样帧数/运动剔除数/去重剔除数/最终关键帧数"；对含明显动作的测试片段，人工抽检漏帧率 ≤ 5%；所有阈值改配置即生效。
- **P0-2 类别体系**：配置 `labels` 已整体替换为施工类别且无交通残留；类别清单覆盖知识库 `visual_keywords` 中的关键对象；`data.yaml` 的 `names` 与配置一致；PPE 缺失由关联推断而非负类检测（有说明文档）。
- **P0-3 知识库注入**：单帧注入文本长度 ≤ `kb_max_chars`；注入内容只含对应场景清单；模型返回的 `hazards[].id` 全部能在知识库中命中（命中率 100%）；`category/norm_reference/action` 由本地回填且与知识库一致。
- **P0-4 双通道**：每个关键帧同时存在 `labels/*.txt`（通道 A）与 `hazards/*.json`（通道 B）；通道 B JSON 必填字段完整率 ≥ 95%（**已达标：`norm_ref` 100% 补全后完整率升至 ≥ 95%**）；`combined_call=true` 时单帧只发生 1 次模型请求（可通过日志/探针验证）。
- **P0-5 模型接入**：主通道标注全程只访问用户自部署的 `base_url`，无任何第三方 API 调用（可通过网络日志/抓包验证）；`probe-qwen` 能返回自部署服务连通性与单帧耗时；对含 thinking 的响应，JSON 解析成功率 ≥ 95%，解析失败帧进入复核队列且原始响应被保留。
- **P0-6 训练闭环**：能生成 `data.yaml` 并完成一次 YOLO 训练；报告含 mAP50/P/R 与混淆矩阵；critical/high 隐患帧出现在困难样本清单中；`next_cycle_tasks.md` 生成。
- **P0-7 mock 模式**：在无视频、无模型的干净环境，一条命令跑通全链路且零报错；输出中显式标注 mock；三类 demo 场景（吊装多隐患/高处违规/无隐患）均能正确产出预期结构。
- **P0-8 配置扩展**：新增字段均有默认值；旧配置文件可直接加载不报错；非法参数（如 `max_keyframes<=0`）触发 `validate()` 报错。
- **可视化（第 4 节）**：生成的 HTML 报告可在浏览器直接打开；关键帧缩略图、检出框、隐患卡片、风险配色、统计图均正常渲染；mock/真实模式标识正确。
