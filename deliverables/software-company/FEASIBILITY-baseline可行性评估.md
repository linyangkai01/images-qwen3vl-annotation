# 可行性评估：当前条件下能否构建可实际运行的 baseline

> 评估时间：2026-09-16
> 评估约束：现有知识库 + 本地工业素材 + 若干单摄像头厂房视频（每段 1 小时，**仅可查看文件名，禁止解析内容，禁止上传模型后端**）
> 评估方法：实测盘点 + 约束推演。全程只列文件名、不解析内容、不上传
> **结论：有条件可行 —— 但必须严格区分两种 baseline**

---

## 〇、结论先行

**有条件可行。**

但这个"可行"有明确的边界，取决于你把 baseline 定义成什么：

**Type A 工程 baseline（链路可运行性验证）→ 可行 ✓**
证明"这条链路是通的、可复现的、可验收的"。

**Type B 业务 baseline（真实检测性能验证）→ 不可行 ✗**
给出"隐患识别准确率/召回率"这类业务指标。

**分水岭就是那三条约束。** 厂房视频不可解析 + 模型后端不可用，等于**同时关闭了数据入口和标注来源**。在这种条件下，任何关于检测精度的 baseline 都建不起来——**不是算力问题，是没有真值**。

## 二、三条约束的实质影响（逐条推演）

### 约束 1：厂房视频仅文件名可见

**可提取**：时间戳、可能的机位编号
**不可提取**：任何画面内容

**影响**：这些视频对 baseline 的**数据贡献为零**。唯一价值是告诉我们「未来会有单机位长视频」，据此**设计接口**（比如源抽象、多机位路由）。

### 约束 2：禁止解析内容

**影响**：**抽帧这一步做不了** → 整条链路的第一步就断了。

这是**最致命的一条**。抽帧是数据供给的入口，入口关闭则下游全空——没有关键帧，就没有标注对象，就没有数据集，就没有训练。

### 约束 3：禁止上传模型后端

**影响**：**VLM 标注做不了** → 通道 A 和通道 B 都产不出标注。

即使抽了帧，也没有标注来源。人工标注是唯一替代，但成本极高。

### 三条叠加的推论

**在厂房视频上，整条链路一步都跑不了。**

这 4 类数据在当前约束下只能作为「未来资源」登记，**不能作为 baseline 的输入**。

## 三、两种 baseline 的区分（回答的核心）

### Type A：工程 baseline（链路可运行性）—— 可行 ✓

**定义**：证明「这条链路是通的、可复现的、可验收的」

**做法**：
1. **抽帧**：用**合成视频**验证（可精确控制真值）。服务器已做过一次：8 秒合成视频（黑→白→红→黄绿），3 处场景切换精确对应 t=2/4/6 秒，4 张关键帧亮度指纹对齐
2. **标注**：用 mock provider 验证结构合规性
3. **数据集**：用 mock 资产跑通切分与 `data.yaml` 生成
4. **训练**：用 mock trainer，或在服务器跑 1-2 epoch 验证命令链
5. **交付**：一条命令端到端零报错 + 全套产物

**这个 baseline 的价值**：证明系统可运行、可交付、可复现。对毕设答辩的「系统完整性」叙事完全够用。

### Type B：业务 baseline（真实检测性能）—— 不可行 ✗

**定义**：给出「隐患识别的准确率/召回率」这类业务指标

**为什么不可行**：

1. **训练数据为 0**
   - 厂房视频不可用（三条约束）
   - 珠海视频无标注
   - 宿州仅 31 张且**无边界框**

2. **评估数据为 0**
   - 无黄金标注 → 算不出 P/R/F1

3. **31 张图不足以训练 12 类检测器**
   - 平均每类 **2.6 张**
   - 检测器训练通常需要每类数百张量级

4. **即使硬训，指标也无统计意义**
   - 验证集与训练集必然重叠
   - 31 张图分 train/val/test 后，每个 split 只有个位数样本
   - 得到的 mAP50 是过拟合的产物，**不可对外声称**

## 四、baseline 的合理范围与预期性能

### 4.1 可测量的指标（现在就能测）

**抽帧层**
- 链路可运行性：端到端退出码 0
- 抽帧压缩比（合成视频可精确控制真值）
- 抽帧漏帧率（合成视频能构造精确真值）
- 9 项计数完整性（`total_frames / sampled_frames / motion_removed / dedup_removed / scene_cuts / force_kept / protected_dropped / display_missing / final_keyframes`）

**标注层**
- 知识库结构合规率：字段完整率（已 100%）、编号命中率（已 100%）
- thinking JSON 解析成功率
- 单帧请求次数（`combined_call` 验证）
- 断点续跑有效性

**工程层**
- 180 个测试通过率
- 阶段产物完整性

### 4.2 不可测量的指标（当前条件无法给出）

- **mAP50 / Precision / Recall** —— 无真实训练数据，任何数字都无意义
- **隐患识别 P / R / F1** —— 无黄金标注
- **真实场景漏检率** —— 无真值
- **端到端延迟 / FPS** —— 无推理服务

### 4.3 关于「预期性能」的诚实回答

**当前条件下无法给出有意义的性能预测。**

原因不是算力不够，是**没有真值**。

如果有人说「mAP50 能到 0.6」，那是拍脑袋——因为训练集不存在、验证集不存在、类别数（12）与样本数（0）严重不匹配。

**唯一可以负责任地说的是**：链路跑通后，第一版模型的指标**大概率不会好看**，原因有三：

1. **单机位固定视角** → 场景多样性差，泛化受限
2. **类间混淆**：`rigging` / `hook` / `load` 视觉相近，容易互相误判
3. **隐患多为「缺失态」**（未戴帽、未系带）→ 检测器只能检实体，违规判定靠空间关联规则。
   **这一步的准确率取决于规则质量，不取决于检测器**——所以即便检测器很准，隐患识别的指标也可能不高

## 五、关键限制与风险

**R1【高】数据入口关闭**
厂房视频不可解析 = 没有长视频数据源。整条链路的第一步就断。

**R2【高】标注来源关闭**
禁止上传模型后端 = VLM 标注不可用。人工标注 300~500 帧 × 12 类的成本很高。

**R3【高】无真值 → 精度指标全部不可信**
直接导致论文的实验章节没有素材，答辩时无法回答「准确率是多少」。

**R4【中】宿州 31 张图无边界框**
只能做分类示例或 few-shot 参考，**不能直接训练检测器**。

**R5【中】珠海视频状态不明**
时长未知、是否受同样约束未确认、4 段仅跨 27 秒（说明是同一次作业的多段）。

**R6【中】单机位固定视角**
模型泛化性天然受限，这是场景属性决定的，不是工程能解决的。

**R7【低】本机无训练能力**
缺 torch/ultralytics，本地只能验证到抽帧段。训练必须上服务器。

## 七、建议的 baseline 定义（务实版）

**推荐：Type A+ —— 工程 baseline 加一条「单视频真实链路」**

具体做法：

1. 用**合成视频**验证抽帧算法（可精确控制真值，能测出漏帧率）
2. 用**宿州 31 张图**构造隐患分类小验证集（**文件名即标签**），验证通道 B 的端到端能力
3. 用**珠海 1 段视频**（若允许解析）跑真实抽帧 → 得到 300~500 关键帧
4. 对这 300~500 帧做**人工抽检**（不要求全标），验证抽帧质量
5. 对其中 **50~100 帧**做标注（mock 或真实 VLM）→ 得到第一份真实小数据集
6. 在**服务器**上训 1 个短 epoch 模型 → 验证训练链路

**这样得到的 baseline 交付物**：
- 一条端到端可运行、可复现的链路
- 一份真实但小规模的数据集
- 一组**工程指标**（压缩比、漏帧率、字段完整率、解析成功率）
- **不承诺精度指标**

**这个 baseline 的定位**：证明「系统能跑，且数据管线是通的」，而不是证明「系统检测得准」。
