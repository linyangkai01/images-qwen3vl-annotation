# 生产可用性差距评估：检测 → 训练闭环

> 评估时间：2026-09-16
> 评估对象：`hazard_annotation/` + `traffic_cv_closed_loop/`（工业施工安全隐患双通道标注链路）
> 评估方法：**代码级核实**，非推测。每条结论标注证据（文件:行）。凡属推断的，明确标「推断」
> 参考基线：生产级「检测→训练闭环」系统应具备的 6 环能力

---

## 〇、一句话结论

**算法链路已成型，工程化基本空白。**

打个比方：现在的系统是一台**能跑通、能演示、能出结果的原型机**，但还不是一条**能 7×24 运转、出问题能发现、模型能自己迭代的产线**。

分两层看完成度：

- **算法与链路层：约 70%。** 核心创新点（双通道建模、知识库本地回填、六步关键帧提取）已成型，180 个测试全绿，真实视频抽帧与真实指标解析都验证过。
- **工程化与生产化层：约 20%。** 没有推理服务、没有监控、没有质量门禁、闭环没有闭合、没有实时采集。

**距离生产级，需要补齐 5 大类共 21 项能力，其中 6 项是 P0 硬门槛。**

---

## 一、先说已经做对的（这是底座，别推倒）

评估要公平，先列出**已经达到生产思路**的部分：

**领域建模是对的**
双通道设计把「检测什么」和「是否违规」拆开了。不设 `no_helmet` 这类缺失态负类，PPE 违规靠 person 框与 helmet 框的空间关联 + 知识库规则推断——这是正确的工程判断，避免让检测器学语义含糊的负类。

**杜绝幻觉的机制是对的**
模型只输出隐患 `id` + `evidence`，`category / norm_reference / action` 全部由知识库本地回填。这从架构上杜绝了模型编造国标号。

**数据质量纪律是对的**
标注阶段**严禁静默丢帧**：解析失败进复核队列且保留原始响应（`tests` 里有对抗用例守着）。断点续跑已实现，已完成的帧会跳过（`hazard_annotation/pipeline/annotation.py:5-6, 246-256`）。

**指标链路是真的**
`_read_results_csv` 从 Ultralytics 的 `results.csv` 真实解析 precision / recall / mAP50 / mAP50-95（`traffic_cv_closed_loop/adapters/yolo.py:27-56`），可视化报告把 mAP50 / P / R 渲染成指标卡（`hazard_annotation/pipeline/visualization.py:254-256`）。不是硬编码的假数。

**隐私与合规设计是对的**
全仓仅一个出网点，无遥测、无云 SDK、无上传逻辑。核心链路零第三方依赖（纯标准库）。

**工程纪律是对的**
180 个测试全绿；mock / 真实双模式；一键 demo 可在无视频无模型的机器上跑通全链路。

## 二、逐维度差距分析

### 维度 A：数据采集与标注

**A1【P0】没有实时 / 流式采集能力**
- 现状：链路入口是 `video.video_path`，只吃**已经落盘的视频文件**（`examples/hazard_project/config/project.json`）
- 生产需要：RTSP / GB28181 / 工业相机 SDK 接入、码流管理、断流重连、采集调度
- 影响：**生产环境不会给你一个 mp4 文件**。没有这一环，系统只能做离线批处理，做不了「检测」本身
- 证据：全仓无 rtsp / stream / camera 相关实现（grep 命中的是文件流等无关匹配）

**A2【P1】没有标注质量管理**
- 现状：无标注一致性校验（IAA / Kappa）、无多人标注比对、无标注审核流、无标注版本回滚
- 生产需要：一致性指标、仲裁机制、标注质量抽检
- 影响：标注漂移会静默污染训练集，且难以定位

**A3【P1】复核队列只落盘，没有复核工具**
- 现状：`review_queue.jsonl` 生成后，人要直接读 JSON 才能复核
- 生产需要：复核界面（哪怕是个本地 Web 页），支持逐帧确认 / 修正 / 批量操作
- 影响：**人工成本直接决定闭环能不能转起来**。没有工具，闭环会因为「没人愿意看 JSON」而停摆

**A4【P1】没有数据分层与均衡采样**
- 现状：六步关键帧提取只管「去冗余、保关键」，不保证**场景分布均衡**
- 生产需要：按场景（吊装/高处）、光照（白天/夜间）、天气、时段分层采样，避免长尾场景样本稀缺
- 影响：模型在长尾场景（夜间、逆光、遮挡）上表现差，而这恰恰是事故高发场景

**A5【P2】没有数据留存与漂移检测**
- 现状：无数据留存策略、无分布漂移检测
- 生产需要：数据留存周期、脱敏机制、输入分布漂移告警
- 影响：现场环境变化（如 LED 光源衰减 15%/30%）会导致数据分布漂移，模型静默退化

---

### 维度 B：模型训练与评估

**B1【P0】没有质量门禁（最危险的一项）**
- 现状：训练跑完就结束，**没有任何「这个模型能不能上」的判断**
- 证据：`hazard_annotation/pipeline/training.py` 与 `adapters/yolo.py` 中无 gate / promote / min_map 等任何门禁逻辑（grep 零命中）
- 生产需要：mAP 阈值卡点、新旧模型回归对比、不达标自动拦截
- 影响：**可能把一个比现役更差的模型推上生产，而且没人知道**

**B2【P0】通道 B 没有量化评估**
- 现状：通道 B（隐患事件）只有两个指标：字段完整率、编号命中率（`annotation.py:202-206`）。这两个是**结构合规指标，不是检测质量指标**
- 生产需要：隐患识别的精确率 / 召回率 / F1。要算这个，必须有「哪一帧真的有什么隐患」的黄金标注
- 影响：**系统最核心的价值（隐患识别）目前无法度量好坏**。答辩时也无法回答「你的隐患识别准确率是多少」

**B3【P1】没有固定评估集治理**
- 现状：`dataset_version = f"v{timestamp_token()}"`（`training.py:92`），train/val/test 每轮重新随机切分
- 问题：**每轮的测试集都不一样，跨轮次指标不可比**
- 生产需要：固定的 holdout 集（最好按时间切分），跨版本可比
- 影响：无法判断「这一轮到底比上一轮好了没有」

**B4【P1】没有实验管理与超参治理**
- 现状：无实验追踪、无配置快照对比、无超参搜索
- 生产需要：实验记录（MLflow 类）、可复现的配置快照、关键超参的调优记录
- 影响：调优靠试，历史结论留不下来

**B5【P1】mock 训练器的指标是公式伪造的**
- 现状：`map50 = min(0.95, 0.45 + 0.04 * min(8, image_count) + ...)`（`adapters/yolo.py:209-211`）
- 说明：这在 mock 模式下是**合理设计**，且输出带 `mock_mode` 标识
- 风险：**容易被误读为真实结果**。论文或答辩若误引，性质严重
- 建议：mock 指标加显式前缀（如 `MOCK-0.65`）或在水印上强制标注

**B6【P2】没有分场景指标拆解**
- 现状：只有全局 mAP50/P/R
- 生产需要：按场景、光照、目标尺寸（小目标）拆解的指标
- 影响：看不到模型在哪个子场景弱

---

### 维度 C：部署与监控

**C1【P0】完全没有推理服务**
- 现状：无模型导出（ONNX / TensorRT / OpenVINO）、无服务化、无 API
- 生产需要：模型导出 → 推理服务 → 接口（HTTP/gRPC）→ 性能基准
- 影响：**「检测」这一半根本落不了地**。现在只有「训练」没有「推理部署」

**C2【P0】没有监控与告警**
- 现状：无指标采集、无日志规范、无告警
- 生产需要：Prometheus 类指标（延迟、吞吐、错误率、GPU 利用率）、结构化日志、阈值告警
- 影响：**生产系统没有可观测性等于裸奔**。模型退化了、服务挂了、准确率掉了，全靠人发现

**C3【P1】没有性能基准与容量模型**
- 现状：无 FPS / 延迟 / 吞吐实测，无「1 小时视频需要多少时间/显存/成本」的估算
- 生产需要：基准测试、SLA 定义、容量规划
- 影响：无法承诺服务能力，无法做成本预算

**C4【P1】没有灰度与回滚**
- 现状：无影子模式、无 A/B、无模型版本切换与回滚
- 生产需要：新模型先影子运行对比，达标再切流；异常一键回滚
- 影响：与 B1（无门禁）叠加，等于**裸奔式上线**

**C5【P1】`base_url` 无本地性护栏（安全）**
- 现状：唯一出网点 `traffic_cv_closed_loop/adapters/qwen.py:535` 的 `urllib.request.urlopen`，目标完全由配置决定，**没有任何校验**
- 生产需要：默认只允许本机/内网，公网地址必须显式开关放行
- 影响：改一个配置字段就能把生产数据发到公网。这是安全审计里的 M1，**至今未做**

---

### 维度 D：闭环反馈与自动化

**D1【P0】闭环没有闭合（最本质的差距）**
- 现状：`hard_examples.jsonl` **只写不读**；`next_cycle_tasks.md` **只写不读**
- 证据：全仓 grep `hard_examples` / `next_cycle`，所有命中都是「写入」侧，**没有任何消费侧代码**
- 生产需要：回流样本自动进入下一轮数据集 → 自动重训 → 自动评估 → 自动决策
- 影响：**现在叫「半自动流水线」，不叫「闭环」**。每一轮都要人工触发，人一停，闭环就停

**D2【P0】没有编排与调度**
- 现状：靠人手敲 `python -m hazard_annotation all`；无 cron、无 Airflow、无任务队列
- 生产需要：定时调度 + 事件驱动（如「新增 N 条复核样本」或「指标跌破阈值」自动触发）
- 影响：没有调度，D1 的自动化也无从谈起

**D3【P1】没有主动学习**
- 现状：困难样本靠「复核队列 + 高危隐患」启发式挑选
- 生产需要：基于不确定性（置信度熵 / 多模型分歧）的采样
- 影响：同样标注预算下，样本效率低

**D4【P1】没有自动化验证（CI for ML）**
- 现状：本地跑测试；无 CI 流水线；服务器靠手工 bundle 同步（本轮才建立通道）
- 生产需要：提交触发测试、数据校验、模型回归
- 影响：改动质量靠人把关

**D5【P2】没有端到端 SLA 定义**
- 现状：PRD 里有指标目标（关键帧 300-500、漏帧率 ≤5%、mAP50 ≥0.60），但没有服务级 SLA（可用性、延迟、时效）

---

### 维度 E：稳定性与可扩展性

**E1【P1】单机单进程，无横向扩展**
- 现状：单进程 + `ThreadPoolExecutor`（`annotation.py:12`）；并发度靠 `qwen.concurrency` 配置
- 生产需要：任务队列、多 worker、多机、背压
- 影响：数据量上去后处理不过来

**E2【P1】只有标注阶段有断点续跑**
- 现状：`annotation.py` 支持跳过已完成帧；但**抽帧、训练阶段没有幂等保证**（`extraction.py` 无 resume 逻辑）
- 生产需要：全链路幂等 + 断点续跑 + 失败重试
- 影响：长任务中断后要重跑，浪费算力

**E3【P1】没有长任务可观测性**
- 现状：无进度上报、无心跳、无超时恢复
- 影响：跑 1 小时视频时不知道跑到哪了、卡没卡

**E4【P1】单路视频，无多机位**
- 现状：配置只有一个 `video.video_path`
- 生产需要：多路并发、跨机位聚合（PRD 里 P2-1 已列为待办）
- 影响：一个工地几十路摄像头，现在只能一路一路来

**E5【P2】外部依赖脆弱**
- 现状：ffmpeg 是外部 CLI 依赖，且有版本硬约束（≥5.1，`ffmpeg.py` 有版本自检）
- 说明：这个设计本身合理（避免重依赖），但**部署时必须确保环境一致**
- 影响：换机器容易翻车。本机就踩过：conda `hazard` 环境消失导致 ffmpeg 不可用

**E6【P2】配置治理薄弱**
- 现状：配置散在 JSON，无 schema 校验版本、无环境分离（dev/staging/prod）
- 生产需要：配置 schema + 版本 + 环境隔离

## 四、补齐重点与建议路径

### 第一条主线：让「检测」真正落地（对应 C1 + A1 + C2）

这是**最该先做**的，因为现在的系统只有「训练」没有「检测」。

1. 模型导出（YOLO → ONNX / TensorRT）+ 推理服务化
2. RTSP / 相机接入，替换「视频文件」入口
3. 指标采集 + 日志 + 告警（延迟、吞吐、错误率、GPU）

做完这条，「检测」这一半才算存在。

### 第二条主线：让「闭环」真正闭上（对应 D1 + D2 + B1）

这是**最能体现系统价值**的。

1. 写一个回流消费器：读 `hard_examples.jsonl` → 生成下一轮数据集 → 触发重训
2. 加调度（cron 或轻量任务队列），支持事件驱动触发
3. 加质量门禁：新模型 mAP 必须 ≥ 现役模型，否则拦截并告警
4. 固定 holdout 集，让跨轮指标可比

做完这条，「模型自己迭代」才成立。

### 第三条主线：让「隐患识别」可被度量（对应 B2）

这是**毕设/论文层面最紧迫**的，因为直接影响能不能写出实验结果。

1. 为一批关键帧建立隐患黄金标注（哪一帧真的有什么隐患）
2. 定义并计算隐患识别的 P / R / F1
3. 分场景（吊装/高处）、分等级（critical/high）拆解

### 第四条主线：安全与稳定性兜底（对应 C5 + E2 + E5）

1. `base_url` 本地性护栏（安全审计 M1，**建议立刻做，成本极低**）
2. 抽帧与训练阶段补断点续跑
3. 环境自检前置（`doctor` 已具备基础，需扩展到依赖版本一致性）

---

## 五、一句话给你的决策建议

**如果目标是毕设答辩**：优先做**第三条主线**（隐患识别量化评估）。现在最尴尬的是「系统很完整，但核心价值没有数字」。补齐 P/R/F1，论文的实验章节就有了。

**如果目标是真上产线**：优先做**第一条 + 第二条主线**。现在的系统在产线上跑不起来，不是因为算法不行，是因为没有推理服务、没有采集、没有监控、闭环不闭。

**无论哪个目标，`base_url` 本地性护栏（C5）都建议立刻补上**——成本半天，收益是堵住唯一的隐私外流口。
