## 四、来源隔离的落地机制（三层防线）

按 `DESIGN-资源来源隔离与存放规范.md` §1.5，原始文件层（`industrial-data`）**物理隔离已不成立**
（开源与自有素材同在该目录下），因此改用**登记表驱动 + 标记文件 + 审计**：

### 4.1 第一层 · 登记表（唯一真源）

1. **位置**：`_index/source_registry.json`（**工作区内**，随仓库版本管理）
2. **结构**：`root_mappings` 数组，把「原始素材根目录 → 来源」显式登记
3. **当前 4 条映射**：

| 目录 | 来源 | 说明 |
|---|---|---|
| `吊装操作视频-珠海` | `own` | 企业私有 · 珠海吊装作业视频 |
| `吊装类安全隐患-宿州基地` | `own` | 企业私有 · 宿州基地吊装隐患照片 |
| **`吊装作业监控-1F-20260716`** | **`own`** | **企业私有 · 本批新增监控录像** |
| `open-ppe-roboflow` | `open` | 开源 PPE 数据集（对比实验专用） |

4. **完整性**：登记表含 `content_hash`（`registry_version + root_mappings` 的规范化 JSON 的 sha256）
5. **来源判定**：**查表**，不按路径推断 —— 查不到即报错阻断（`SRC-010`），绝不默认归类

### 4.2 第二层 · 标记文件

1. 每个来源子目录内放置 `SOURCE.json`，内容 `{source, source_ref, license, registered_at}`
2. **须与登记表对应条目逐字段一致**，不一致即报错阻断（`SRC-002`）
3. 校验结果：**4 个目录全部一致 ✓**

### 4.3 第三层 · 审计

1. **变更留痕**：`_index/registry_changelog.jsonl`（谁在何时改了哪个目录的来源）
2. **事后扫描**：`verify_no_cross_source()` 校验工作区产物 + 登记表完整性 + `SOURCE.json` 一致性
3. 本次变更已留痕（`action: "add_mapping"`）

### 4.4 ⚠️ 诚实声明（不夸大防线）

登记表 + 标记文件 + 审计**属「约定 + 校验」，不是物理隔离**。

若有人在**同一来源子目录内混放另一来源的文件**，**且同时**篡改 `SOURCE.json` 与登记表哈希，
则单靠静态检查**无法发现** —— 此时只能依靠逐素材 `content_hash` 溯源 + 人工抽检。

**本机制只保证：混放要么被门禁阻断，要么在登记表 / changelog / 审计中留痕。**
