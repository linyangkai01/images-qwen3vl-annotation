## 〇、一页结论

报告里列的 8 个问题，**性质完全不同，不能一起治**。按根因分四类：

**A 类 · 口径问题（不是模型问题，改报告 + 改参数就见效，零成本）**

1. `overall = 0` 是宏平均假象 → 换汇报口径
2. 9 帧 holdout 不可用于交付判断 → 改双轨制
3. `load` / `overhead_crane` 的 P=1.0 / R=0.02 → 先扫 conf 阈值，大概率不是"学不会"
4. 三档验收「档内取最差」→ 在 1:140 不均衡下等价于永远 fail，设计本身有问题

**B 类 · 数据问题（最高性价比，不动模型）**

5. `hook` / `rigging` 疑似标注混淆 → 程序化排查，74 框可全量人工复核
6. 帧冗余 → 去重后再送标注，减少 VLM 调用量
7. 小目标 `helmet` / `vest` → 采集端 ROI 裁剪，等效放大 2×

**C 类 · 模型 / 流程问题**

8. 初检召回过低 → 换开放词汇检测器（YOLO-World，ultralytics 原生支持，集成零成本）
9. 小目标检测 → SAHI 切片推理 + P2 头 + 改用原帧训练

**D 类 · 外部依赖问题（需要老总去协调）**

10. VLM 标注 15.9 小时 → **换 Instruct 权重是最大杠杆（预期 10×+）**，但端点不归我们管
11. 47% 隐患缺几何 / 时序推理 → 几何层可自研（约 100 行）；时序层需先改抽帧率

**最重要的一句话**：报告把「模型学不会」和「报告口径不对」混在一起了。`load`/`overhead_crane`/`hook`/`rigging` 这四类，很可能根本不是"学不会"，而是**阈值问题**和**标注问题**。**先做 A 类（零成本）和 B 类（低成本），再决定是否投入 C / D 类。**

## 问题 1 · `overall = 0` 是宏平均假象

**先纠正一个事实性细节**

- 【已验证】COCO 官方 mAP = 各类 AP 的**宏平均（macro）**，不按样本数加权。
- 【已验证】COCO 对缺失类的处理分两种：某类**在评估集无 GT** → AP 置 −1 并**排除**出均值；某类**有 GT 但零检出** → AP = 0 且**计入**均值。
- 所以：`hopper` / `ebike`（零样本、无 GT）本该被排除，但 7 类「有 GT 零检出」是**真实缺陷**，不能拿「缺类忽略」来辩解。**`overall = 0` 是诚实信号，不是 bug** —— 问题在于它把 `person` 0.667 / `balance_beam` 0.764 的进展完全掩盖了。

**对策 · 三层汇报口径**

1. 主指标改 **micro-mAP**（把所有类的框聚合计算，反映总体工作量分布）
2. 宏平均 mAP 保留，但**必须注明被几类零值主导**
3. **逐类 AP + 该类 GT 框数 + 置信区间** —— 这才是决策依据
4. 宏平均的「类集合」设门槛：只纳入 **gt ≥ 10~15 框**的类；`pallet`(gt=2) 不报 mAP，改报命中/漏检计数

**每类最少多少 GT 才有意义**

- 无官方硬标准（Ultralytics issue #2438 被 closed as not planned，属经验非规范）
- 【已验证】LVIS 把 <10 实例的类定义为 AP_r，并公认噪声极大
- 【推断】工程经验：每类验证集 **≥15~30 框**才稳，**≥20~50 框**才有参考价值

## 问题 2 · 9 帧 holdout 不能用于交付判断

**方法 · 小样本 mAP 的置信区间**

【已验证】正确做法是 **image-level bootstrap**（按**图像**有放回重采样）：

1. 推理一次并缓存全部预测
2. 每轮有放回抽图像（连同该图全部 GT + 预测）
3. 重算 mAP / P / R，取分位数得 95% CI
4. 重采样次数：探索 100~500 / 标准 1000 / 交付 5000~10000

**关键**：**不要按框或按类重采样** —— 同图内检测框不独立（一个 FP 会改变同图其它框的匹配），按框采样会**低估方差**。

CI 宽度解读：`<0.05` 稳定 / `0.05~0.10` 谨慎比较 / **`>0.10` 不可比**。

【推断】你的 9 帧 holdout 上 person P 在 0.102 / 0.180 / 1.000 之间跳、R 恒 = 1.000，正是「CI 宽度 ≈ 1.0」的退化状态：**bootstrap CI 几乎覆盖 [0,1]，任何跨轮比较都无统计意义**。R 恒为 1 说明该 9 帧 person GT 极少且每帧至少命中一框，是退化样本。

**对策 · 双轨制（有先例的通用工程模式）**

- **轨道① 冻结 holdout**：哈希保持不变，**降级为「无回归门禁」** —— 只要求新版本不低于旧版本，**不作为绝对达标依据**；报告里必须写明 CI 极宽
- **轨道② 独立大评估集**：做绝对性能验收。你的 31 帧分层集就是它，但**需要扩样**：要使某类 AP 的 95% CI 宽度 ≤ 0.1，通常需该类 **≥30~50 个 GT 框**，且**覆盖 ≥3~4 段独立视频**（避免同源帧相关）

## 问题 3 · `load` / `overhead_crane` 高 P 低 R

**成因**（P=1.000，R=0.022~0.034）：模型对这些类**输出置信度普遍偏低**（正样本少 → logit 没拉开），在 `conf=0.25` 下几乎不触发。**这不是"学不会"，是"没被叫醒"。**

**零成本对策（按顺序做）**

1. `model.val(conf=0.01)` 看 PR 曲线，用 **F1 最大点**替代 0.25
2. `cls` 损失权重从默认 0.5 提到 **1.0**
3. `label_smoothing=0.0`（平滑会压低稀有类峰值）
4. 检查 TAL 正样本分配（`topk` / `alpha`）—— 正样本过少会放大该问题
5. 补该类困难样本（数据侧根治）

## 问题 4 · 三档验收全部 fail

0.7 / 0.5 / 0.35 三档**本身常见**（源自 COCO / VOC 常识锚点），不是问题。

**问题在「档内取最差类」**：在 1:140 不均衡 + 7 类零值下，「取最差」等价于「永远 fail」，把 `pallet`(gt=2) 的**采样噪声当成一票否决**，既掩盖头部类进展，又无法推进交付。

**建议改为四层**

1. **安全关键类双门限**：整体（样本加权）达标 **且** `person` / `helmet` / `vest` / `harness` 逐类 ≥ 阈值；其余类只要求「不回归」
2. **GT 门槛过滤**：每类设最低 GT 框数（如 ≥15）才参与打分，未达门槛的类**只做定性检查**
3. **CI 门限**：要求指标 **CI 下界** ≥ 阈值，杜绝用噪声点估计过关
4. **双轨门禁**：冻结 holdout 做「无回归」，大评估集做「绝对达标」

## 问题 5 · `hook` / `rigging` 未学会 —— 样本量不是主因

**关键反证**：`balance_beam` 训练集只有 42 框却到 **0.764**；`hook` 35 框却是 0。**只差 7 框，说明主因不是数量。**

**可能主因（按可疑度排序）**

1. **标注混淆** —— hook 常挂在 rigging 末端，视觉相邻相似，共现 13 次
2. **类内形态方差大** —— `balance_beam` 是固定长条横梁；`hook` 随吊装角度 / 远近形态剧变
3. 背景混杂 / 遮挡 —— hook 常与 rigging、负载重叠
4. 评估集该类 gt 太少，0.02 的 R 统计上本就不可靠

**程序化排查方案（可直接执行）**

1. **跨类 IoU 重叠**：FiftyOne `compute_max_ious(dataset, "gt", classwise=False)` —— **必须 `classwise=False`**，默认 True 抓不到 hook↔rigging 的跨类重叠
2. **共现矩阵**：统计 13 次共现里两框的**中心距 / 面积比**分布；若大量框近乎重合（IoU > 0.5）即确证标错
3. **面积 / 长宽比分布**：hook 应偏小、rigging 应偏长条，画箱线图对比，离群即疑
4. **工具**：FiftyOne（推荐，内置 IoU / 重复检测）、CVAT（人工复核）、labelCloud（仅标注）
5. **人工抽样**：`hook` + `rigging` 共 **74 框全量逐一看**（量小可全查），其余类每类抽 20%

**若确证混淆，两条路**

- **合并类**（hook 并入 rigging，35 → 74 框）：低风险、立刻见效，代价是失去细粒度
- **保持分开 + 重标**：保留细粒度，但要重标 74 框并重训

## 问题 6 · 稀有类学习手段评估（重要：别走错路）

**【已验证】损失函数改造性价比最低**

- Focal / EQL v1,v2 / Seesaw / Class-Balanced / LDAM —— **无一可直接用于 Ultralytics YOLO**。YOLO 默认分类损失是 BCE，需改 `utils/loss.py` 自定义 `v8DetectionLoss`
- Seesaw 论文只在 Mask R-CNN（两阶段）验证（LVIS +6.0 AP），作者明言**单阶段需额外解耦 objectness，未在单阶段验证**
- 【推断】对 173 张图的小数据集，**损失重加权的收益 < 数据侧清洗**

**【已验证】真正适配小数据的两个办法**

1. **Decoupling 两阶段训练**（Kang 2019 / ICLR2020）：阶段 1 全量 instance-balanced 训练学表征；阶段 2 解冻 head，只在稀有类上微调（cRT）。论文核心结论：**不平衡不影响表征学习，只需重平衡分类器**
2. **Simple Copy-Paste**（Ghiasi 2021）：单阶段与两阶段均显著增益

**【冲突 · 必须先自测】**

Ultralytics 的 `copy_paste` 参数：官方文档称需 polygon 标签、仅 segment / OBB 适用；但 issue #6590 维护者称 bbox 检测可用。**先小样本自测验证再投入**，否则徒劳。

## 问题 7 · `helmet` / `vest` 小目标 —— 物理限制

已实测：helmet 框短边中位数 **10.8px**、96% 的框 < 32px；在 960×540 上约 **38.4×21.6px**。
【已验证】COCO 定义 **<32×32px 为小目标** —— 你的 helmet 本就低于阈值。

**方案（按性价比排序）**

**7.1 【最优先 · 极低成本】吊装 ROI 裁剪**

只取画面上部（吊装作业区），等效把 helmet 放大约 **2×**。不换设备就能做，收益立竿见影。

**7.2 【高收益 · 低成本】SAHI 切片推理**

【已验证】SAHI 论文（ICIP 2022，VisDrone / xView 验证）：

- 仅切片**推理**：AP50 **+5.1~6.8%**
- 叠加**切片微调**累计：**+12.7~14.5%**
- xView 小目标 AP50s：从 0.1~0.5 升到 **12~15**
- 25% overlap 再加 **+1.7%**
- 注意：全图推理（FI）对大目标 +3.3%，但小 / 中目标略降

用法：

```
pip install -U ultralytics sahi
AutoDetectionModel.from_pretrained(model_type="ultralytics", model_path="best.pt",
                                   confidence_threshold=0.3, device="cuda:0")
get_sliced_prediction(img, model, slice_height=384, slice_width=384,
                      overlap_height_ratio=0.25, overlap_width_ratio=0.25,
                      perform_standard_pred=True)
```

针对你的场景（960×540、目标 10~30px）：slice **320~384**、overlap **0.25~0.3**、`postprocess_match_threshold=0.5`（GreedyNMM 默认合并重复框）。

【已验证的坑】

1. 切片过小 → `person` / `overhead_crane` 等大目标被切断，大目标 AP 下降
2. 跨切片目标只被部分看到 → 漏检（靠 overlap 缓解）
3. 重复框靠 NMM 合并，阈值不当 → 框抖动
4. **173 图小数据集做切片训练 = 有效样本再减少 + 上下文丢失，可能反而变差** → **先把 SAHI 只用在推理端**，切片训练单独做消融实验

**7.3 【中成本】P2 检测头**

官方自带 `yolo11-p2.yaml`（Detect(P2,P3,P4)，P2 stride=4，专为小目标）。
`YOLO("yolo11s-p2.yaml").load("yolo11s.pt")` —— **可用 COCO 预训练迁移，不必从头训**。
代价：参数量 / GFLOPs / 显存上升，速度下降（24G 显存需降 batch）。

**7.4 【关键修正】训练分辨率用错了方向**

当前用 **640×360 缩图**训练是错的方向。应把标注 **×1.5 还原到 960×540 原帧**，配：

- `imgsz=1280` → helmet ≈ 28.8px
- `imgsz=1536` → helmet ≈ 34.6px（才够 32px 阈值）

**7.5 【调参】**

- `scale` 从默认 0.5 降到 **0.2~0.3**（默认会随机缩小，小目标更小）
- 保留 `mosaic=1.0` + `close_mosaic=10`
- YOLO11 是 anchor-free，**无 anchor 参数**
- 173 图下 imgsz 越大有效增强样本越少、过拟合风险越高 → 务必早停

**7.6 【不推荐】纯上采样 / 超分**

- 纯双三次上采样（640→1280）：**不增加任何信息**，YOLO 内部本就会 letterbox 到 imgsz，喂 1280 与喂 640 + imgsz1280 **等价** → **无用**
- 【已验证】MDPI Sensors 2024 综述：SR 预处理总体提升目标检测，COCO 上小目标提升率比全体高 9.4%；GAN 类（Real-ESRGAN）即便 PSNR/SSIM 下降仍能提升检测；但 HAT/DAT 在 BI 退化下 PSNR 升而检测反降
- 【推断】Real-ESRGAN 靠「幻觉」补纹理，对小目标可能微增，但引入伪影 + 预处理成本 → **仅作备选**

**7.7 【兜底】两阶段 ROI 分类**

若 `imgsz=960` + P2 + SAHI 下 helmet 仍 <0.1，说明 10px 不可分。转两阶段：只训 `person`（人框大易学），在 person bbox 内**裁剪上采样**后用小分类器判 helmet / vest（ROI 内等效放大数倍，是小目标的成熟做法，R-CNN 式）。

## 问题 8 · 两段式降本假设失败

**根因一句话**：**用闭集检测器做开放词汇任务。** `yolo11n.pt` 是 COCO 80 类闭集，吊钩 / 吊索具 / 平衡梁 / 料斗**根本不在 COCO 里**。

### 8.1 初检器换成开放词汇检测器 —— YOLO-World 已进 ultralytics，工程零成本

```python
from ultralytics import YOLOWorld
m = YOLOWorld("yolov8x-worldv2.pt")
m.set_classes(["hook", "sling", "overhead crane", "spreader beam",
               "hopper", "worker with helmet"])
m.predict(source, imgsz=1280, conf=0.1)
m.save("safety_world.pt")   # 固化离线词表
```

【已验证】

- 官方文档：`set_classes` 免重训动态换类；**v2 支持导出 ONNX / TensorRT**（原版不支持）；零样本 COCO mAP：s 37.7 / m 43.0 / l 45.8 / x 47.1
- 速度（G-DINO 1.5 论文 Table 5，A100 / 640px）：YOLO-Worldv2-S **47.4 FPS** / M 42.7 / L 37.4
- 精度更高的替代：**Grounding DINO 1.5 Edge**（A100 PyTorch 21.7 FPS / TensorRT 111.6；LVIS-minival 36.2 AP，超 YOLO-Worldv2-L 的 32.9）

【推断】

- 4090 单帧预计 15~25ms；YOLO-World s 级 640px 显存约 2~4GB，4090 24GB 充裕
- **G-DINO / OWLv2 / DINO-X 集成难度高**（独立 repo）；DINO-X 主要为 API，速度 / 显存未公开

【关键】小目标（10~30px）在 640px 下召回仍低 → **必须 `imgsz≥1280` 或叠加 SAHI**。纯换模型不够。

### 8.2 标注角色转换：VLM 从「标注员」→「审核员」

- 用开放词汇检测器零样本产出候选框 → 人工**只做删 / 改 / 补**，而非从零画框
- 【已验证】迭代伪标签自训练：**MixPL**（混合伪标签，缓解 confirmation bias）、Dense Teacher、Label Matching SSOD 均验证 —— 少量真标 + 大量过滤伪标签可逼近全监督
- 关键：伪标签 **conf 阈值过滤** + 强弱增广

### 8.3 帧级去冗余（送标注前先降量）

- 415 帧 / 1908s ≈ 4.6s/帧，静止场景仍有大量近重复
- 【推断】CLIP / DINOv2 嵌入 + 聚类 + 每簇取代表帧，可削减 **3~4×**（415 → 100~150）；**精确比例需实测**
- ultralytics 内置 `model.track()`（ByteTrack），只在「新目标出现 / 状态变化」时抽帧
- 参考实现：Video-Frame-Deduplication（CLIP）、arXiv 2506.00667（场景检测 + 关键帧）

### 8.4 主动学习

- 【已验证】**PPAL**（CVPR2024，开源 `ChenhongyiYang/PPAL`）：两阶段 = 难度校准不确定性采样（分类 + 定位加权）+ 类别条件相似度 + k-Means++ 多样性采样；**不改架构，可直接配 YOLO**，论文称大幅优于随机采样
- 开源可用：`baal`、`modAL`；**FiftyOne 官方 Active Learning 插件基于 modAL**；FiftyOne ↔ Label Studio 有官方集成
- 【冲突 / 谨慎】论文多在 COCO 万级验证；415 帧下推断选 30~40%（约 130~160 帧）可接近全量指标，但**这个规模「全标」本身不贵**，AL 的真正 ROI 在**后续新视频流的持续筛选**

## 问题 9 · VLM 标注 15.9 小时（占全链路 97.5%）

### 9.0 先做归因（用分项字段，不要只看墙钟）

```
排队时长 = total_duration − (load_duration + prompt_eval_duration + eval_duration)
稳态速度 = eval_count / eval_duration
```

【已验证 · 推论】

- 323 帧 × 176s ≈ 15.8h ≈ 总时长 15.9h → **几乎无排队损耗**
- 60~119KB 响应约 1.5~4 万 token，176s → 约 **100~250 tok/s**，符合 MoE（3B 激活）单流速度
- **结论：约 95% 时间花在生成 thinking token 上** —— 不是排队、不是冷加载（load 仅首批约 159s）

这与「关 `enable_thinking` / 降 `max_tokens` 无效」的实测完全一致：该 Q8 权重是 **thinking 专用版**，reasoning 已固化进权重。

### 9.1 【最高杠杆 · 成本最低】换 Instruct 权重

- 【已验证 · 事实】Qwen3-VL-30B-A3B 的 **Instruct 与 Thinking 是两套物理独立的权重**。Instruct 不产 reasoning trace，输出从数万 token 降到数百~数千
- 【推断 / 需自测】某 WEBUI 镜像实测（RTX4090D）：同任务 Instruct **1.8s vs Thinking 12.6s**，显存 14.2GB vs 21.7GB → 预期 **10×+**。该数据来自营销向博客、非严格 benchmark，**必须自测**
- ⚠️ **这是外部依赖**：端点 `119.23.145.227:38091` 不归我们管，需要老总去协调部署方换权重
- 风险：安全标注是否依赖推理链，需用同一批帧跑两版、对比标注质量

### 9.2 【中 · 高成本】vLLM / SGLang + 连续批处理

- 【已验证】vLLM 支持 `Qwen/Qwen3-VL-30B-A3B-Instruct`（FP8、`--enable-expert-parallel`、`--tensor-parallel-size`）；SGLang 支持 30B MoE（BF16/FP8、`--tp` / `--ep`）。二者均做 continuous batching，远优于 Ollama
- 【已验证】SGLang 官方吞吐（B200×8，235B-A22B）：并发=1 → 91.8 tok/s；**并发=100 → 873.8 tok/s、峰值 2855 tok/s**（约 10× 吞吐）。⚠️ 这是 235B 在 8×B200 上，**不能直接外推到 30B 单卡**，仅作量级参考
- ⚠️ **硬约束**：Q8_0 ≈ 32GB / FP8 ≈ 32GB，**单张 4090 24GB 放不下**（需 40GB+：A100 40/80、H100）。4090 只能走 AWQ / GPTQ int4（约 17GB）+ KV，或 2×4090。注意 SGLang 文档仅列 BF16 / FP8，**未列 AWQ**；vLLM 支持 AWQ

### 9.3 【低优先】Ollama 开并发 —— 收益有限、易 OOM

- 【已验证】默认 `OLLAMA_NUM_PARALLEL=1`、`OLLAMA_MAX_LOADED_MODELS=3×GPU数`、`OLLAMA_MAX_QUEUE=512`；**内存 ∝ NUM_PARALLEL × CONTEXT_LENGTH**（官方例：2K context × 4 并发 = 8K）
- **关键**：Ollama 的 parallel 是**同一模型多份 KV cache / 上下文**，不是共享前缀的真正批处理。32GB 模型单卡余量本就小，KV 翻倍极易 OOM 或 offload 到 CPU（更慢）
- 【推断】**除非显存 ≥80GB，`num_parallel` 不会提升吞吐，只会排队 / OOM**
- 若仍要试：`OLLAMA_NUM_PARALLEL=2~4`、`OLLAMA_MAX_LOADED_MODELS=1`、`OLLAMA_KEEP_ALIVE=-1`、`OLLAMA_FLASH_ATTENTION=1`、`OLLAMA_KV_CACHE_TYPE=q8_0`、`OLLAMA_CONTEXT_LENGTH=8192`

### 9.4 【不要指望】结构化输出 / 提示词约束

- `format`（JSON schema）：能约束最终 JSON，但 thinking 权重**会先生成 reasoning 再输出 JSON**，抑制 thinking 效果有限
- 提示词「只输出 JSON」：对 thinking 专用权重基本无效（与实测一致）
- `num_predict` 与 `max_tokens` 本质相同；**设小会先截断 thinking，导致最终 JSON 缺失，不可靠**
- **唯一可靠解法是换 Instruct 权重（9.1）**

### 9.5 【低收益】输入侧降分辨率

- 【已验证】Qwen3-VL patch size 由 14 改 16（下采样因子 32），环境变量从 `MAX_PIXELS` 改为 `IMAGE_MAX_TOKEN_NUM` / `IMAGE_MIN_TOKEN_NUM`；`IMAGE_MAX_TOKEN_NUM=768` 对齐旧 `MAX_PIXELS=602112`
- 降 `scale_width` 使视觉 token 近似平方下降，但**视觉 token 仅数百 vs 输出数万 token → 提速有限**，且可能损害小目标 / 隐患检出 → **不建议优先**

### 9.6 【最直接 · 低风险】多机并行 + 幂等重试

- 323 帧拆多机 / 多实例，近似线性提速
- 端点不稳（2.2~132s 波动），加超时 + 重试 + **幂等**（已标注的帧跳过）

## 问题 10 · 47% 隐患需几何 / 时序推理（能力缺口）

### 10.1 几何关系推理层（可自研，约 100 行几何函数，无需训练）

可复用的几何启发式（来源 arXiv:2607.27145 的 SpatialAnalyser —— ⚠️ **该来源冷门、引用极少，仅作阈值参考**）：

- 框 `b = (x_l, y_t, x_r, y_b)`，中心 `c = ((x_l+x_r)/2, (y_t+y_b)/2)`
- **重叠率 OR = 交面积 / min(面积i, 面积j)** —— **用 min 而非并集**，才能识别「小框在大框内」。`OR > 0.70` → inside；`0.10 < OR ≤ 0.70` → touching
- **邻近**：归一化中心距 `d = ‖ci−cj‖ / √(W²+H²)`，`d < 0.30` → near
- **方向**：`cy_i < cy_j` → above；`cx_i < cx_j` → left
- **优先级**：containment > contact > vertical/horizontal > proximity

**`D-5-3`「人在吊物正下方」算法【推断，建议实现】**

1. 水平投影重叠 `HOR` = 水平区间交 / min(宽i, 宽j)，要求 person 中心落在 load 的 x 区间内（或 `HOR ≥ 0.5`）
2. 垂直关系：`person.y_t ≥ load.y_b`（人整体在吊物底边之下）
3. 垂直间隙 `g = person.y_t − load.y_b`，要求 `0 ≤ g ≤ k·load_height`（k ≈ 1.5，坠落影响锥）
4. person / load 得分 ≥ 0.4 才参与判定
5. 三条同时满足 → 判「站在吊物正下方」

**危险区**：以 `overhead_crane` / `hook` 为锚，取 hook 地面投影点为中心、半径 `r = α·load_height` 的圆 / 矩形；person 中心落入即告警。
**接触判定**：`rigging` / `hook` 与 `load` / `scaffold` 的 `OR ≥ 0.10` 判接触。

**框误差鲁棒性（重要，否则结论不可信）**

1. 关系用**带滞回阈值**（判定 `OR ≥ 0.55`、撤销 `OR < 0.45`）防边界抖动
2. 对框各边 **±2~5px 扰动重算**，输出「稳定 / 临界」标记
3. 置信度门槛 0.4~0.5，低于不判
4. 优先用**包含 / 接触等面积型关系**（对定位误差不敏感）；方向型（正下方）最脆弱，须靠「间隙 + 投影」双重条件兜底

参考：Visual Genome / VSR 空间关系数据集；SGG 综述；awesome-scene-graph；apple/ml-gbc 的 bbox 空间关系编码。**无即插即用库**，建议自写。

### 10.2 时序推理（7 条）

【已验证 · 可行范式】YOLO 检测 + ByteTrack 轨迹 + 时序统计 / 卷积判异常（Nature Sci Rep 2026）。

【已验证 · 参数】Ultralytics ByteTrack 默认：`track_high_thresh=0.25`、`track_low_thresh=0.1`、`new_track_thresh=0.25`、`track_buffer=30`、`match_thresh=0.8`；BoT-SORT 另加 `proximity_thresh=0.5`、`appearance_thresh=0.25`（默认关 ReID）。

【冲突提示】BoxMOT 库的 BoT-SORT 默认值不同（`track_high_thresh≈0.63`、`match_thresh≈0.77`、`track_buffer=40`）—— 那是调优预设，**勿混用**，须锁定一套并写明。

**「吊物悬停」算法【推断】**

- 对每条 track 维护轨迹 `{(t, cx, cy, w, h)}`
- 滑动窗口 `W = 2~3s`，算窗口内 load track 的中心位移标准差 `σ_center` 与平均速度 `|v|`
- 判据：`σ_center < δ_px`（如 5px 或 <5% load 尺寸）**且** `|v| < v_thr` **且** track 持续 ≥ W **且** 期间无操作信号

⚠️ **硬瓶颈**：当前抽帧 31.8min → 415 帧 ≈ **0.22fps**，2~3s 窗口只有 0~1 帧 → **必须按 5~10fps 重新抽帧**才能做时序推理。**这一条要先决策。**

### 10.3 可验证性设计（工程模式「证据三元组」）

每条隐患结论落盘结构化 JSON：

```
{hazard_id, rule, rule_version, verdict, confidence,
 subjects: [{class, bbox, track_id, score}],
 geometry: {OR: 0.62, HOR: 0.71, gap_px: 34, ...},
 thresholds_snapshot: {...}, window: {t0, t1, frames: [...]},
 overlay_path: "evidence/D-5-3_001.jpg", status: "stable|borderline"}
```

- 落盘**叠加框 + 数值标注的取证图**（画 person / load 框、投影区、危险区、OR / HOR / gap 数值）
- 时序附**轨迹坐标序列 + 迷你图**
- 判定标 **stable / borderline**；borderline 自动进人工复核队列 → 把黑箱结论变成「可秒判的带证据结论」
- 保留**规则版本号 + 阈值快照**，支持结论回溯复现
