# 第一部分 · 立项初衷（先立准，再谈方案）

## 1.1 核心问题

甲方工厂手上有**大量未标注的真实监控素材**，覆盖吊装作业，希望实现安全隐患的自动检测。但面临三重冷启动困境：

1. **零标注** —— 没有任何标签数据，从零标
2. **人工标注贵** —— 工业场景标注需要懂吊装作业的专人，纯人工成本不可接受
3. **通用模型不认** —— 吊钩、吊索具、平衡梁这些工业专用件**不在 COCO 里**，通用 YOLO 检不出（实测：YOLO 657 框 vs VLM 1553 框）

**一句话核心问题**：如何用**最低的人工成本**，从零标注的工业素材中冷启动出一个可用的吊装场景检测模型。

## 1.2 目标用户

| 角色 | 是谁 | 关切 |
|---|---|---|
| **最终受益方** | 甲方工厂安全管理人员 | 能不能检出隐患、误报多不多 |
| **直接用户** | 本项目算法/交付团队 | 链路能不能跑通、指标能不能交代 |
| **工程实现方** | 编码组（外包/并行） | 规格是否明确、验收是否可测 |
| **素材提供方** | 甲方现场 | 素材能否持续供给 |

【假设】甲方具备持续供给同场景素材的能力；若只有这一批 4 段视频，则本项目的产出上限被数据规模锁死，需降级为"技术验证"而非"产品"。

## 1.3 使用场景

**离线批处理**（不是实时）：

```
周期性（如每周/每批）接收工厂监控视频
  → 离线跑「抽帧 → 初筛 → 标注 → 训练 → 评估」
  → 产出/迭代检测权重与报告
  → 人工只看复核队列
```

【假设】未来可能部署到现场做实时告警，但**本期明确不做**（需求 1.3.7）。方案需为未来部署留出接口，但不为其支付成本。

## 1.4 功能边界

**做**：

```
F1 素材编目与抽帧（视频解码、关键帧筛选）
F2 吊装场景类别体系（12 类）+ 与隐患知识库（58 条）映射
F3 两段式半自动标注（通用/开放词汇初检 → VLM 复核 → 质量过滤）
F4 版本化数据集构建（data.yaml + manifest + 划分 + 冻结 holdout）
F5 YOLO 冷启动训练与评估
F6 困难样本回流 + 复核队列
F7 隐私护栏（素材不出网、来源隔离）
```

**不做**（需求 1.3，逐条有理由）：

```
✗ 高空作业场景（素材缺失）
✗ 修改母项目 traffic_cv_closed_loop/ 任何一行
✗ 主链路新增第三方依赖
✗ 本机 Windows 跑全量测试/训练
✗ 公有云/第三方多模态 API
✗ 模型部署、推理服务化、实时告警
✗ 开源资源与自有资源混放
✗ 交付隐患结论报告（降级为内部手段）
```

## 1.5 可衡量的成功标准

**现行标准**（需求第 7 节，按目标像素尺寸分档）：

```
A 档（短边 ≥100px）：mAP50 ≥ 0.70 且 召回 ≥ 0.80
B 档（32~100px）   ：mAP50 ≥ 0.50 且 召回 ≥ 0.65
C 档（<32px）      ：mAP50 ≥ 0.35 且 召回 ≥ 0.55
硬性要求：必须逐类报告，不允许只给平均值
```

**⚠️ 现行标准的可达性问题（必须正视）**

实测：12 类中只有 `person`(0.667) 和 `balance_beam`(0.764) 有指标，**其余 8 类 ≈ 0**。按"档内取最差类"判定 → **三档永远 fail**，团队无法判断自己是否在进步。

**我建议的成功标准优化**（详见第三部分）：

```
L0 必达（工程）：链路可跑通、守恒校验通过、数据集可复现
L1 必达（质量）：建立验证集，给出准确率/漏检率的实测数字
L2 分层达标（模型）：
    核心类（person / balance_beam / overhead_crane）达到 A/B 档
    稀有类（spreader / pallet）如实标注"样本不足，不可学"
    小目标类（helmet / vest）按 C 档考核，并注明像素物理下限
```

## 1.7 对当前立项方案的优化建议（自主思考）

读完全部材料后，我认为立项有 **6 处需要优化**：

**优化 1 · 交付物定义分层（当前模糊）**

现状：需求说"交付检测权重"，但实际又产出了 197 条隐患报告，导致边界不清、甲方预期错位。

改为三层，**各层独立验收**：

```
L0 数据集（可复现、可校验）     ← 工程交付
L1 检测权重（逐类指标）          ← 模型交付（本期主交付物）
L2 隐患报告（内部产物，不交付）  ← 仅用于提升标注质量
```

**优化 2 · 成功标准改为分层门禁（当前不可达）**

见 1.5。核心改动：**放弃"档内取最差"，改为"安全关键类双门限 + 稀有类如实披露"**。

**优化 3 · 把"建立验证集"从可选项提升为必达项**

没有 ground truth，所有"准确率提升"的说法都无法证实。**这是本项目最大的方法论缺口。**

**优化 4 · VLM 端点抽象成可替换 Provider（⚠️ 前提已修正）**

**前提修正（2026-09-26）**：原文"当前 403 导致全链路瘫痪"**不成立** ——
实测端点正常（用项目代码调用成功、检出 3 个目标）。403 系 curl 手工构造请求时
token 少读 3 字符所致，**非端点问题**。

**该优化仍值得做，但理由应改为**：架构解耦（便于未来更换模型/端点）、
离线可测性（`pseudo` provider 让 CI 不依赖外部服务）。支持三种实现：
`private_vlm`（当前）/ `local_ollama`（降级）/ `pseudo`（离线测试用）。

**通用教训（建议写入协作约定）**：探测外部服务**必须用项目自己的调用路径**，
不要用 curl 手工构造 —— 容易在 token / header 上出错并导致误判。

**优化 5 · 数据集划分改为按视频分组（当前有泄漏）** ⭐ 本次新发现

`dataset.py:466-476`：

```python
pool = sorted(accepted, key=lambda r: r.candidate.relative_path)
train = pool[:train_count]      # 前 70%
val   = pool[train_count:...]   # 后 20%
```

按路径排序后**按数量切一刀** → 每个视频源的**前段进 train、后段进 val**。

**问题**：同���视频相邻帧间隔仅约 4.6 秒，画面高度相似。val 里的帧与 train 里紧邻它的帧几乎是同一画面 → **泄漏，指标虚高**。且 val 只覆盖每个视频的尾部时段 → **评估偏差**。

**改法**：按 `source_id` 做 **GroupShuffleSplit**，并在 train/val 的时间边界处**留时间缓冲**（如 ≥30 秒），避免紧邻帧跨集。

**优化 6 · 评估集扩容 + 多 seed 降噪（当前噪声太大）**

9 帧 holdout 上 `person` 的 Precision 在 0.102 / 0.180 / 1.000 之间跳 —— 无法用于交付判断。
改：评估集扩容 + **3 seed 取均值**（4090D 训一轮 10 分钟，3 seed 完全可行）+ 报置信区间。

# 第二部分 · 技术选型及理由

## 2.1 已选技术

| 领域 | 选型 | 理由 | 证据 |
|---|---|---|---|
| **检测框架** | Ultralytics YOLO | 项目已用、生态成熟、自带增强/追踪/导出 | 已跑通 50 epoch / 10.6 分钟 |
| **模型规格** | **yolo11s/m 或 YOLO26s（不用 x）** | 33 模型基准：小数据集上 **x 系列反而过拟合** | arXiv 2411.00201 |
| **视觉标注** | Qwen3-VL-30B-A3B（私有端点） | 唯一合规途径；能出框+隐患双通道 | 已产出 1553 框 |
| **小目标结构** | **P2 检测头** | **+0.036 mAP50**，helmet 10.8px 正对口 | SOD-YOLO VisDrone 实测 |
| **后处理** | **Soft-NMS** | **+0.050 mAP50 且零 FLOPs** | SOD-YOLO 实测 |
| **长尾** | **离线过采样 + BACL 式两阶段** | LVIS rare AP **1.1→16.0**，frequent **零损失** | BACL CVPR |
| **初检（待替换）** | **YOLOE 视觉提示** | 工业件语言难描述，**视觉提示可用示例框定义** | Ultralytics 内置 |
| **轨迹/时序** | Ultralytics ByteTrack | 内置，零依赖 | 已有 temporal.py |
| **视频切分** | PySceneDetect（离线工具） | 5.2k stars、活跃 | 视频去冗余最成熟 |
| **标签质检** | cleanlab.object_detection | 置信学习在检测上**唯一活跃实现** | 11.7k stars |
| **数据探索** | FiftyOne | `compute_mistakenness` 支持 Detections | 11.1k stars |

## 2.2 被否决方案（含取舍说明）

| 方案 | 否决理由 |
|---|---|
| **DVC / LakeFS / Git LFS** | 292 样本 + 单服务器 + 离线受限。装 dvc + 配 remote 的成本 > 收益。改用 `MANIFEST.json` + 只读目录 |
| **MLflow / W&B** | W&B 云端（出网禁令下不可用）；MLflow 依赖重。用 `runs/index.jsonl` + 配置快照（10~20 行代码） |
| **自建 VLM 服务** | 老总明确否决（2026-09-25） |
| **多视角 3D 重建（VGGT/DUSt3R）** | 输出**尺度歧义（非米制）**；VGGT 明确败于大面积运动物体（吊物正是）；无 3D 真值可验证 |
| **单目深度估计（DAv2）** | 信噪比约 1:1，误差与 2D 投影歧义同量级 → **净负担** |
| **改损失函数（Seesaw/EQLv2）** | 无任何 Ultralytics 适配实现；对 292 条收益 < 数据侧清洗 |
| **Ultralytics `copy_paste`** | 官方文档：**需 polygon 标签，纯 bbox 的 detect 不生效**。改用 `cutmix` 或自写 |
| **知识蒸馏** | 教师模型自己 8 类为 0，软标签在长尾类上全是噪声 |
| **CLOD / safednn-clean** | **已废弃**（8 stars，2023-03 停更）。改用 cleanlab |
| **DINO-X / Grounding DINO 1.6** | **只有云 API**，违反不出网硬约束 |
| **Real-ESRGAN 超分** | 2024-08 停更；对伪标签小目标会引入伪影 |
| **Airflow / Prefect / k8s / Docker** | 离线批处理脚本即可，编排平台超配 |
| **Great Expectations** | 自写 20 行断言足够 |
| **structlog / ELK / Prometheus** | 标准库 logging + `run.jsonl` 足够 |

# 第四部分 · 开发流程、分支与提交规范

## 4.1 分支模型（简约版，适配小团队）

```
main            ← 始终可运行；只接受 PR
feat/<短名>     ← 功能分支
fix/<短名>      ← 修复
exp/<短名>      ← 实验（允许失败，不删，保留结论）
```

**不开** `develop` / `release` / `hotfix` —— 小团队超配。

## 4.2 提交规范（Conventional Commits 简化版）

```
<type>(<scope>): <subject>

type: feat | fix | refactor | test | docs | chore | exp
scope: video | dataset | train | eval | pipeline | providers | docs
```

示例：

```
feat(dataset): 划分改为按 source_id 分组并加时间缓冲
fix(active_learning): 复核判据改用按类分档阈值
exp(train): P2 头消融（helmet mAP50 +0.03）
```

**规则**：
- 一个提交只做一件事
- `exp/` 分支的提交必须说明**结论**（哪怕失败）—— 实验的价值在记录
- **禁止** `--no-verify` 常态化（pre-commit 只放 5 个 hook，避免过慢）

## 4.3 PR 规范

```
必填：改了什么 / 为什么 / 怎么验证 / 影响范围
必过：ruff + 单测 + 数据测试（fixture）
需要人工确认的：涉及验收口径、隐私边界、母项目
```

# 第五部分 · 质量保障

## 5.1 测试策略（分层金字塔）

```
顶层  training/    真实数据 1-epoch 冒烟 + 离线评估
      ↑ @pytest.mark.training，--strict-markers，默认不跑
      ↑ 手动或 nightly（4090D 一轮 10 分钟，可行）

中层  integration/ 合成 fixture（几张 64×64 假图）端到端，秒级
      ↑ 每次 push 都跑

底层  unit/ + data/   纯函数 + 数据校验，秒级
      ↑ 每次 push 都跑
```

**禁止每个测试都读真实数据** —— 用合成 fixture。

## 5.2 数据测试（必做，成本极低）

```
✓ txt 每行 5 列，class_id ∈ [0, C-1]
✓ bbox 归一化 ∈ [0,1]，w/h > 0
✓ 图-标签同名一一对应
✓ 空标签率在阈值内
✓ 类别直方图 vs 上次快照差异 < 阈值（防 VLM 重标后类别崩塌）
✓ ★ 划分泄漏检查：同 source_id 的相邻帧不跨 train/val（时间缓冲 ≥30s）
✓ 重复图像检测（sha256）
```

## 5.3 模型回归测试（关键：不要用硬门禁）

**问题**：9 帧评估集上单帧变化就能让 mAP50 抖几个点。硬门禁会天天误报，最后被手动绕过。

**做法**：

```
1. 粗下限防彻底崩塌：如 mAP50 > 0.30 → 低于则 fail
2. 相对基线：下降 > X% → 只 warn，不 fail
   X 必须等于"评估集噪声尺度"，建议 5~10 个点
3. 降噪：评估集扩容 + 3 seed 取均值 + 报置信区间
4. ★ 只按【安全关键类】（person/balance_beam/overhead_crane）设门禁
   稀有类（spreader/pallet）如实标注"不可学"，不设门禁
```

## 5.4 静态检查

```
ruff（format + lint 一体）
  → 放 [project.optional-dependencies].dev
  → ★ dependencies = [] 保持不变（PEP 621 extras，零依赖约束不受影响）
  → pre-commit hook 走独立环境，不污染主环境

mypy
  → 6100 行存量不要求全量 strict（性价比低）
  → 新代码加注解；★ 跨层接口（数据层/评估层）必注解

pre-commit（只 5 个 hook，避免过慢）
  → ruff-check --fix      （必须在 ruff-format 之前）
  → ruff-format
  → check-yaml
  → end-of-file-fixer
  → ★ check-added-large-files   ← 正好防工业素材误入 git，契合"不出网"
```

## 5.5 持续集成（CI）

**核心约束：素材不出网 → 云端 runner 永远碰不到真实数据。**

```
CI 分两层：

【快集】每次 push，<2 分钟，云端或本地
  → ruff
  → 单测 + 数据测试（合成 fixture）
  → import 冒烟
  → config schema 校验 + MANIFEST 校验

【慢集】手动或 nightly，自托管 runner（同一台服务器）
  → 1-epoch 训练冒烟
  → 离线评估 + 指标快照
  → 产出"基线候选"，★ 人工确认后才晋升为基线
```

**训练不进 push 级阻塞门禁** —— GPU 独占 + 指标噪声，会拖垮日常开发。

⚠️ **自托管 runner 的安全要求**：必须使用 **private repo**。公开仓库 + 自托管 runner 有严重安全风险。

# 第七部分 · 里程碑与最小可用版本落地顺序

## M0 · 可复现基座（1~2 天）★ 最小可用版本

**目标**：任何人 checkout 后能跑通并得到**可复现**的结果。

```

```

**验收**：泄漏检查通过；同配置 3 seed 的指标方差可接受。

```
9. 复核判据改为按类分档 + P25 标定 + 三态（pass/reject/review）
```

**验收**：复核队列从 322 帧降到 60~100 帧。

## M3 · 建立验证集（1~2 天 + 人工预算）★ 质量地���

